# 數據集生命週期

> 測試集從設計到退役的完整管理框架

## 概述

資料集並非靜態資產，而是需要持續維護的動態資源。Nie et al. (2020) 指出：「隨著模型進步，資料集可能失去區辨力；隨著時間推移，資料可能過時或洩漏。」

---

### 完整生命週期

| 階段 | 核心任務 | 研究參考 |
|------|----------|----------|
| **設計** | 需求分析、規格定義 | Bowman & Dahl (2021) |

| **使用** | 評測執行、結果記錄 | — |

| **更新** | 補充、修正、擴展 | Zhu et al. (2023) |
| **退役** | 歸檔或廢棄 | — |

## 設計階段

### 需求分析

在建立資料集前需明確：

| 問題 | 考量 |
|------|------|
| 評測目標是什麼？ | 特定能力 vs 通用能力 |
| 目標模型是什麼？ | 規模、類型、應用場景 |
| 如何衡量成功？ | 指標選擇、通過標準 |
| 有何限制？ | 時間、預算、倫理 |

### 規格設計

Bender & Friedman (2018) 的 Data Statement 框架建議記錄：

- **語言變體**：地區、年代、正式程度
- **說話者特徵**：人口統計、專業背景
- **收集情境**：時間、來源、目的
- **標註過程**：指引、人員、品質控制

## 建立階段

### 資料來源選擇

| 來源類型 | 優勢 | 劣勢 |
|----------|------|------|
| **生產日誌** | 真實性高 | 隱私問題、分佈偏斜 |
| **公開資料** | 易取得 | 可能已被訓練 |
| **眾包收集** | 規模大 | 品質控制困難 |
| **專家編寫** | 品質高 | 成本高、多樣性有限 |

### 品質驗證

多層次品質控制：

| 層次 | 方法 |
|------|------|
| **交叉驗證** | 多人標註同一筆資料 |
| **專家審核** | 領域專家抽樣核實 |
| **試運行** | 用已知表現的模型測試 |
| **統計分析** | 檢查分佈異常 |

## 發布階段

### 資料集卡片

Gebru et al. (2021) 提出的 Datasheet for Datasets 框架：

| 區塊 | 內容 |
|------|------|
| **動機** | 為何建立此資料集 |
| **組成** | 資料內容與格式 |
| **收集過程** | 如何收集 |
| **預處理** | 進行了哪些清洗 |
| **用途** | 適合與不適合的任務 |
| **分發** | 授權與取用方式 |
| **維護** | 聯絡方式、更新計畫 |

### 版本控制

| 實務 | 說明 |
|------|------|
| 語義化版本 | Major.Minor.Patch |
| 變更日誌 | 記錄每次修改 |
| 不可變發布 | 已發布版本不修改 |

---

## 監控階段

### 資料污染檢測

Sainz et al. (2023) 提出的污染檢測方法：

| 方法 | 原理 |
|------|------|
| **成員推斷** | 測試模型是否「記住」特定樣本 |
| **重疊分析** | 檢查與已知訓練集的重疊 |
| **困惑度分析** | 異常低困惑度可能表示見過 |

### 分佈偏移監控

| 監控項目 | 警示情況 |
|----------|----------|
| 模型表現趨勢 | 分數持續上升可能表示污染 |
| 生產資料分佈 | 與測試集分佈差異擴大 |
| 題型難度 | 原本困難題目變簡單 |
