# Defense Against Indirect Prompt Injection via Tool Result Parsing

## 摘要（中文翻譯）

隨著 LLM agent 從數位助理轉向自主系統與機器人的實體控制器，它們面臨間接 prompt injection（IPI）日益嚴重的威脅。攻擊者將對抗性指令嵌入工具呼叫結果中，劫持 agent 的決策過程以執行未授權操作。現有防禦機制分兩類：訓練專用偵測模型（計算開銷大、需頻繁更新）和基於 prompt 的方法（靈活但攻擊成功率仍高）。本文提出一種新方法，透過工具結果解析（tool result parsing）為 LLM 提供精確資料，同時有效過濾注入的惡意程式碼。該方法在保持競爭性任務效用（UA）的同時，達到迄今最低的攻擊成功率（ASR），顯著優於現有方法。

## 問題背景

LLM agent 在處理工具呼叫結果時，面臨間接 prompt injection 的嚴重威脅——攻擊者在工具回傳的資料中嵌入惡意指令，劫持 agent 行為。現有防禦方法存在明顯缺陷：偵測模型需高計算成本且難以跟上攻擊演化；prompt-based 方法的攻擊成功率（ASR）仍然偏高，對精密攻擊缺乏魯棒性。隨著 agent 對實體環境的控制增強，這個問題的危險性也在升級。

## 解決方案

提出 ParseData + CheckTool 雙模組防禦方法。核心洞察是：工具結果包含的資料遠多於 agent 實際需要的，而合法資料符合特定格式（如電子郵件格式、日期格式、數值範圍），注入指令無法滿足這些嚴格要求。ParseData 模組讓 LLM 根據預期資料格式解析工具結果，僅提取必要資訊；CheckTool 模組驗證工具呼叫的合法性。這種方法不依賴攻擊偵測，而是透過資料格式約束自然過濾惡意內容。

## 核心貢獻
1. 提出基於工具結果解析的間接 PI 防禦新範式，透過資料格式約束自然過濾惡意指令，不需專門的攻擊偵測模型
2. 達到迄今最低的攻擊成功率（ASR 0.1%-0.5%），同時維持競爭性的攻擊下效用（UA），風險指標（ASR/UA）低至 0.2%-1%
3. 方法為 prompt-based，無需額外訓練，可直接部署於現有 LLM agent 架構

## 技術方法

**ParseData 模組**：在 agent 處理工具結果前，先由 LLM 根據工具的預期輸出格式（如 email 格式、日期、數值範圍等）解析結果，僅提取符合格式的結構化資料，丟棄不符合預期的內容（包括注入的指令）。

**CheckTool 模組**：驗證 agent 選擇的工具是否與當前任務相關，防止攻擊者透過注入指令誘導 agent 呼叫非預期工具。

**評估設置**：在 AgentDojo benchmark 上測試，使用三個目標模型（GPT-OSS-120B、Llama-3.1-70B、Qwen3-32B），對比五種基線方法（DeBERTa Detector、Repeat User Prompt、Spotlighting with Delimiting、Tool Filter）。衡量指標包括 ASR（攻擊成功率）、UA（攻擊下效用）和 Risk（ASR/UA 比值）。

## 關鍵結果

| 方法 | 平均 ASR | 平均 UA | 平均 Risk |
|------|---------|---------|----------|
| 無防禦 | 20%-30% | — | — |
| Tool Filter（最佳基線） | 5%-7% | — | 3%-6% |
| Repeat User Prompt | — | — | 6%-12% |
| **ParseData+CheckTool** | **0.1%-0.5%** | 競爭性 | **0.2%-1%** |

*在 Important Messages 攻擊（最嚴重場景）下，ParseData+CheckTool 的 ASR 為 0.1%-0.5%，遠低於 Tool Filter 的 5%-7% 和無防禦的 20%-30%。*

## 對我們的啟發
- [ ] 「資料格式約束」作為防禦策略的有效性表明，PI 防禦不必依賴攻擊偵測——透過限制 agent 能「看到」的資訊格式，可自然隔離惡意指令，這是一種更魯棒的防禦思路
- [ ] 此方法對 tool-calling agent 特別有效，因為工具的輸入/輸出格式通常是可預測的，但對自由文本場景（如聊天、文件摘要）的適用性可能有限
- [ ] 未能防禦「參數劫持」（parameter hijacking）暴露了格式約束防禦的盲點——攻擊者可在合法格式內替換參數值（如更改收款人 email），需要額外的語義驗證層

## 限制與未來工作

方法專注於防禦未授權工具呼叫，但無法防範「參數劫持」——在合法工具呼叫中替換參數值（如將付款地址改為攻擊者的）。目前缺乏專門針對參數劫持的綜合 benchmark。此外，ParseData 的效果依賴工具結果的格式可預測性，對結構化程度低的工具可能效果不佳。
