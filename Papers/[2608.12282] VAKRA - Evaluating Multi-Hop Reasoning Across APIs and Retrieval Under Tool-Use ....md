# VAKRA: Evaluating Multi-Hop Reasoning Across APIs and Retrieval Under Tool-Use Policies

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.12282)
- 📥 [PDF](https://arxiv.org/pdf/2608.12282v1)

## 摘要（中文翻譯）

企業環境中的 agents 必須同時處理結構化 APIs 與文件集合，但既有 benchmarks 多半分開評估這些能力。本文提出 VAKRA（Evaluating API and Knowledge Retrieval Agents），涵蓋 62 個 domain、超過 8,000 個可執行 APIs，並設計三種遞增難度的任務：多樣化 API 互動風格、結構化 API 上的 multi-hop reasoning，以及受 natural-language tool-use policies 約束的 multi-source reasoning。系統透過重新執行預測的 tool calls 驗證 correctness，並允許多條有效路徑。作者使用固定的 ReAct harness 以隔離模型能力與 agent architecture。結果顯示，最佳模型在單跳 endpoint-style 任務僅達 70.4%，在 compositional APIs 降至約 50–51%；隨 reasoning depth 增加，性能下降超過 50%。Policy-constrained questions 尤其困難，unanswerable queries 的準確率最低僅 2.4%。Trace analysis 指出，主要失敗來自 entity disambiguation、cross-source grounding 與 schema alignment 等 language-mediated reasoning，而非 tool invocation mechanics。

## 問題背景

現有 tool-calling、web navigation、multi-hop retrieval、policy adherence 與 agent benchmarks 多在隔離環境測試，無法反映企業工作流中 API、文件與自然語言政策的連鎖依賴。特別是 entity disambiguation、異質 schema 對齊、跨來源 grounding，以及政策使問題不可回答時的判斷，缺少可執行且可驗證的整體評估。

## 解決方案

作者提出 VAKRA，一個本地可執行、資料庫與文件集合共同支援的 agent benchmark。它以超過 8,000 個 APIs 和 62 個 domain 為基礎，將 API styles、結構化 multi-hop、API+retrieval multi-source reasoning 及 tool-use policies 組織成遞增難度設定。固定 ReAct harness 控制 agent architecture 變因；trajectory-level verifier 重新執行工具呼叫並比對必要資訊，允許 alternate valid paths，再分別評估答案 groundedness、correctness 與 policy adherence，從而定位語言推理而非單純工具操作的瓶頸。

## 核心貢獻
1. 提出 VAKRA benchmark：在 62 個 domain 中提供超過 8,000 個以真實資料庫為後端、可本地執行的 APIs，並配對 domain-aligned document collections。
2. 建立 2–5 hop 的 compositional 任務，將 API interaction、document retrieval 與 natural-language tool-use policies 納入同一條 reasoning trajectory。
3. 提出 trajectory-level waterfall evaluation：重新執行預測 tool calls、允許 alternate valid paths，並分離 tool sequence、final grounded answer 與 policy adherence 的失敗來源。

## 技術方法

VAKRA 的工具環境以單一 Docker image 本地部署：結構化工具由 62 個 BIRD-SQL domain 的 SQLite 資料庫支援，文件檢索使用各 domain 的 ChromaDB collection，並以 IBM granite-embedding-english-r2 建立索引。API 提供三種介面：SLOT 使用 9 個通用操作組合流程；SEL 將參數化函式展開為 26 個可選工具；Dashboard APIs 則提供每個 sample 可見的高度專用 endpoint，工具數可達 116。資料生成先從 BIRD-SQL 查詢抽取 entities，映射到 Wikidata5M，建立 API connectivity graph，再以 depth-first traversal 產生 1–3 hop 鏈；後續加入 Wikipedia/ClapNQ passage，生成 API+RAG 問題與 multi-turn retrieval 對話，並以 LLM-based filtering 排除 API 與 RAG 之間的 answerability contamination。多跳任務涵蓋 2–5 steps，部分加入限制來源選擇的 natural-language policies。每個模型均包裝在相同的 LangGraph ReAct agent 與 MCP tool interface 中。評估採 waterfall：先重新執行 predicted tool calls，透過 programmatic containment check 及 GPT-OSS-120B judge 驗證是否取得必要資訊；通過者再以 LLM judge 評估 final answer 的 groundedness 與 correctness；policy 任務另以 deterministic check 驗證是否呼叫禁用來源。資料品質研究抽樣每種設定 60 題，由三位 annotators 以 faithfulness、logical consistency、answer leakage、context sufficiency 與 cross-source entity consistency 五項 1–4 分量表評估。

## 關鍵結果

| 模型 | BI APIs (SEL) | BI APIs (SLOT) | Dashboard APIs | Multi-hop Reasoning | Multi-source Multi-hop | Avg. Score |
|---|---:|---:|---:|---:|---:|---:|
| GPT-5.5 | 51.0% | 50.0% | 70.4% | 52.4% | 26.0% | 50.1% |
| Gemini-3-Flash-Preview | 38.6% | 39.0% | 60.3% | 36.9% | 16.7% | 38.7% |
| Claude-Sonnet-4.5 | 35.3% | 38.4% | 49.5% | 38.1% | 17.3% | 35.9% |
| Qwen-3.5-397B | 42.3% | 47.8% | 46.7% | 30.0% | 16.6% | 37.1% |
| GPT-OSS-120B | 40.1% | 42.7% | 50.5% | 25.1% | 15.5% | 35.0% |

補充結果：GPT-5.5 在 Dashboard endpoint-style 任務達 70.4%，在 SEL 與 SLOT compositional BI APIs 分別為 51.0% 與 50.0%。多數模型隨 reasoning depth 增加而損失超過 50% 的準確率。Policy-constrained unanswerable queries 的準確率最低為 Claude Opus 4.7 的 2.4%。論文未報告所有 hop 數與各模型的完整逐跳數值。

## 對我們的啟發
- [ ] 評估企業 agent 時不應只測 endpoint-style function calling；應同時涵蓋 SLOT、SEL 等 compositional interfaces，因為模型在不同 API paradigm 的排名可能反轉。
- [ ] 系統改進應優先處理 entity disambiguation、跨來源 grounding、長工具回應的資訊抽取與 schema/parameter alignment，而不只是增加工具數量或改善工具呼叫格式。
- [ ] 對不可回答情境應設計明確的 policy-aware abstention 與 answerability checks；VAKRA 顯示模型可能在政策禁止必要來源時仍強行回答，這對企業流程與合規部署具有實務風險。

## 限制與未來工作

資料主要由 BIRD-SQL、Wikidata5M 與 ClapNQ 經 pipeline 及 LLM 輔助生成，雖有小型人工品質研究，但仍可能存在生成偏差與 shortcut artifacts。評估固定於 ReAct harness，未比較 planner、memory 或其他 agent architectures；Stage 1、Stage 2 亦部分依賴 GPT-OSS-120B 作為 LLM judge。論文未提供完整的人工 judge 校準、統計顯著性與真實企業流量驗證。
