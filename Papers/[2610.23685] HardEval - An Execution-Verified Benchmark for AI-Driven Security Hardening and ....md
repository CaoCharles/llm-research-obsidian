# HardEval: An Execution-Verified Benchmark for AI-Driven Security Hardening and Compliance Remediation

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2610.23685)
- 📥 [PDF](https://arxiv.org/pdf/2610.23685v1)

## 摘要（中文翻譯）

實作 Security Technical Implementation Guide（STIG）控制項，是一項具挑戰性的作業系統管理工作。每項自然語言安全要求都必須被轉換為精確且持久的設定變更，涵蓋 SSH、身分驗證政策、稽核規則與 kernel 參數。既有 benchmark 無法衡量模型在 live system 上完成此任務的能力：程式碼 benchmark 通常評估沒有持久系統狀態的孤立程式，而 agent benchmark 多聚焦於應用程式。本文提出 HardEval，一個以執行驗證的 AI security hardening benchmark。它取自未強化 RHEL 8 baseline 上失敗的 DISA STIG controls，以專家撰寫的 remediation 與 OVAL checks 作為隱藏 ground truth。模型只能看到安全結果要求，必須產生 Bash script；script 會在 live VM 執行，再由 OpenSCAP/OVAL 檢查是否由 fail 轉為 pass。十四種模型配置顯示，不同安全領域的能力差異顯著且不均衡；常見失敗是產生看似合理、卻不符合精確 compliance condition 的安全程式碼。HardEval 已公開提供。

## 問題背景

論文要解決的是：LLM 能否將自然語言 STIG 要求轉換為可持久化的 OS hardening code，並使 live system 通過權威 compliance scanner。既有 HumanEval 等程式碼 benchmark 缺乏持久系統狀態，SWE-bench 與 agent benchmark 主要針對 repository、應用程式或互動環境；安全評測則多衡量漏洞避免或攻擊能力。因此，現有方法無法直接測量 Bash remediation 是否讓作業系統由 fail 轉為 scanner-verified pass。

## 解決方案

作者提出 HardEval，一個針對 RHEL 8 OS hardening 的 execution-verified benchmark。資料由未強化主機的 OpenSCAP 掃描建立，保留 STIG rule、專家 reference remediation 與 OVAL check 作為隱藏答案。每個任務只向模型提供 implementation-withheld 的自然語言目標、理由、必要值與持久性要求，不揭露檔案路徑、directive、sysctl key 或命令。模型以 single-shot 方式產生 Bash script，script 在乾淨、可丟棄的 AlmaLinux 8 VM 執行，最後以相同 OVAL rule 判定 fail-to-pass。此設計將 code-generation capability 與 retrieval、agent orchestration 及 scanner feedback 分離。

## 核心貢獻
1. 提出 HardEval execution-verified benchmark，以 live VM、Bash remediation 與 OpenSCAP/OVAL fail-to-pass grading 評估 LLM 的 OS hardening 能力。
2. 建立 implementation-withheld prompt 與隱藏 reference remediation、OVAL oracle 的資料建構流程，將模型能力與 retrieval、orchestration 及 scanner feedback 分離。
3. 對十四個 frontier 與 open-weight configurations 進行基準研究，揭示模型在 server、audit、SSH 等安全領域的結構化能力差異，並提供多次執行、跨作者提示與 Ubuntu 24.04 portability 驗證。

## 技術方法

HardEval 的資料來源是 RHEL 8 DISA STIG profile 下、使用 SCAP Security Guide 0.1.81 進行的 OpenSCAP scan。初始有 233 條失敗規則，其中 215 條具 reference Bash remediation，200 條屬於 automatable tasks；跨模型固定 manifest 包含 151 條 verified-applicable rules，其中排除 SSH 後的 server-safe 集合為 137 條。提示由 Claude Opus 4.8 根據 rule title、severity、rationale 與 description 生成，但不使用 reference script；系統提示要求保留安全目標、閾值、idempotency、reboot persistence 與 scope，同時刪除實作機制，並以 lexical-leakage checker 檢查機制詞洩漏。模型收到單一 prompt、不可使用工具或檢查主機，並以 temperature 0 產生一份 Bash script。每個配置在獨立 throwaway AlmaLinux 8 VM 上執行；sanitized PATH 會阻止 reboot、shutdown、poweroff 與 systemctl reboot。執行後重新呼叫 OpenSCAP 1.3.14，只有 OVAL 結果為 literal pass 才計分；invalid、空白或未評分輸出均視為失敗。主要指標是各 bucket 的 pass 數除以固定分母，包括 server configuration plus kernel、audit rules、combined server-safe、SSH 與 all verified applicable。研究評估十四個 closed frontier 與 open-weight configurations，另以四個 open-weight 配置進行三次 seeded runs，使用 pooled Wilson 95% confidence intervals；並測試 GPT-4o authored prompts 與 Ubuntu 24.04 port。

作者報告 frontier 模型佔據前七名，最強 open-weight 配置為 DeepSeek-Coder-33B 的 35.8%。Audit-rule construction 是差異最明顯的領域。四個 open-weight 配置的多次 Wilson intervals 保留單次評估排序；Qwen-14B 與 CodeLlama-34B 區間仍分離，而 GLM-4-9B FP16 與 4-bit 區間重疊。GPT-4o authored prompts 上，Claude Opus 4.8 為 101/137 (73.7%)、GPT-4o 為 73/137 (53.3%)。Ubuntu 24.04 的 88 條 shared rules 中，Claude Opus 4.8 為 60/88 (68.2%)、GPT-4o 為 55/88 (62.5%)、Claude Sonnet 5 為 53/88 (60.2%)。

## 對我們的啟發
- [ ] 若要評估自動化安全修補，不應只檢查 shell 語法或文字相似度；應在隔離 VM 執行後，以外部 compliance oracle 驗證實際終態。
- [ ] 安全程式碼的合理性不等於合規性；實務部署需要特別檢查 scanner 所要求的精確值、檔案、directive、audit key 與設定機制。
- [ ] 聚合分數可能掩蓋 domain-specific weakness，尤其 audit-rule construction 與 server configuration 應分開報告；SSH 等可能影響評估通道的控制項也需獨立解讀。

## 限制與未來工作

研究僅涵蓋 RHEL 8 DISA STIG 的 curated、automatable 子集；Ubuntu port 顯示方法可移植，但未證明跨 RHEL 9、Windows 或其他 profiles 的結果一致。十個配置只有單次 greedy run，variance study 未涵蓋 closed models；SSH 可能因共用 grading channel 而低估。作者亦指出 STIG 公開資料造成 training-data contamination 的可能性，以及 oracle satisfaction 不等於廣義安全性。未來將擴展至 RHEL 9 與 Windows STIG。
