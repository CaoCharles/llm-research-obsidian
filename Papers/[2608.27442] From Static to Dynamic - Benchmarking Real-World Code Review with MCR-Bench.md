# From Static to Dynamic: Benchmarking Real-World Code Review with MCR-Bench

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.27442)
- 📥 [PDF](https://arxiv.org/pdf/2608.27442v1)

## 摘要（中文翻譯）

在真實軟體開發中，code review 通常由開發者與 reviewer 透過反覆互動共同改善軟體品質，因此成本高且耗時。雖然近期研究開始使用大型語言模型（LLM）自動化 code review，多數方法仍將其簡化為單輪、靜態的決策任務，無法呈現實際審查中的多輪互動與複雜問題解決過程。為彌補此缺口，作者提出 MCR-Bench，首個具備 defect state awareness、面向真實多輪 code review 的 benchmark。資料集涵蓋 Python、Java、JavaScript、TypeScript 與 C# 五種語言，包含 2,269 個真實多輪 code review tasks；每項任務皆標註細粒度 defect metadata 與跨輪 state labels，以記錄 defect 的完整演化軌跡。實驗顯示，主流 LLM 在 defect detection 與 defect lifecycle state tracking 上整體能力有限，且隨互動輪數增加而明顯退化；模型對不同 defect type 與 severity 的表現差異很大，語義複雜或不顯著的 defect 更容易被遺漏。錯誤分析進一步指出，跨輪時間錯位與不足的長程記憶是重要失敗機制。

## 問題背景

現有 LLM code review benchmark 多集中於 function、diff hunk、commit 或單輪 PR 層級，通常只要求模型根據初始程式狀態產生一次性回饋。這種設定忽略真實 review 中的「review→revision→revalidation」循環，也無法判斷 defect 是否持續存在、已解決、重新出現或由新問題取代，因此不足以評估模型的跨輪記憶、時間一致性與 defect lifecycle tracking 能力。

## 解決方案

作者提出 MCR-Bench，將 code review 建模為具備歷史脈絡與 defect lifecycle 的多輪 PR-level 評測任務。每個 task 同時提供固定的 PR metadata 與 linked issues，以及隨輪次更新的 code diff、review timeline 和互動紀錄；ground truth 則以 defect cards 表示，包含 defect description、location、taxonomy、severity，以及每輪的 New、Open、Resolved 或 Reopened 狀態。資料建構採用「先局部偵測、後全域追蹤」策略，先逐輪抽取候選 defect，再跨輪合併同一問題並推斷狀態轉移，最後由人工交叉驗證。

## 核心貢獻
1. 提出 MCR-Bench，將真實 code review 從單輪靜態判斷提升為具備跨輪 defect state evolution 的多輪 PR-level benchmark，涵蓋五種語言與 2,269 個 task。
2. 建立「local detection first, global tracking later」的 LLM-based state-aware 資料建構流程，並結合三次一致性過濾與六名開發者的人工 cross-validation。
3. 以 defect type、severity、interaction depth 與 lifecycle state 為分析維度，系統評估主流 LLM 的 defect identification 和 state tracking 能力，並建立 false positive/false negative 的 failure-root-cause taxonomy。

## 技術方法

MCR-Bench 的資料流程包含四階段。第一，依 GitHub 活躍度選擇 Python、Java、JavaScript、TypeScript 與 C#，並保留具備超過 100 stars、近五年持續提交、issue resolution rate 超過 40%、超過 10 位 contributors、至少 1,500 個 PR、採 permissive license 且非 fork 的 repository。第二，收集 merged PR，排除只修改非程式檔案、初始 commits 超過 10 個、缺乏「commit→discussion→revision」循環或含 automated bot 互動的樣本，並用 SZZ-2 排除後續被確認為引入 bug 的 PR。第三，進行 LLM-based state-aware annotation：Phase I 將 PR 依 review round 拆分，只以該輪 diff 與 comments 偵測候選 defect；Phase II 彙整候選項目，跨輪合併 defect identity，並根據後續 commits、歷史 feedback 與 defect mentions 推斷每輪 lifecycle state。每項任務獨立執行三次，只有 defect description 與 state transition 完全一致者保留。第四，由六名具五年以上經驗的開發者進行 cross-validation；兩名主要 annotator 獨立審查，不一致時交由第三人仲裁，主要 annotator 的 Cohen’s kappa 為 0.87。資料集共 2,269 tasks，平均 3.8 輪、最多 10 輪，每 task 平均 2.37 個 defect。評估面向包括 defect identification、lifecycle state prediction、跨輪表現變化、false positive/false negative 根因，以及 comment quality。論文指出曾比較 BLEU-4、ROUGE-L、LLM Scoring 與 LLM-Hit-Judge，但所提供文字未包含最終指標選擇與完整評估公式。

## 對我們的啟發
- [ ] 實務上的 automated code review 不應只在單一 diff 上產生 comments，還應保存 defect identity、歷史 comments、後續 commits 與目前 state，以支援持續驗證與避免重複或過時回饋。
- [ ] 評估系統應將 defect detection 與 defect lifecycle tracking 分開量測；模型指出問題不代表能正確判斷問題是否已解決、仍開啟或重新出現。
- [ ] 多輪部署需要特別測試長程記憶與時間對齊能力，並針對低顯著性、語義複雜及不同嚴重度的 defect 分層分析，而不能只報告單一總體分數。

## 限制與未來工作

論文提供的內容未呈現完整實驗表格、各模型具體分數、最終評估指標公式及 baseline 適配細節，限制了結果的可重現比較。資料只涵蓋五種語言、38 個 GitHub repositories，且只保留 merged、許可授權且通過 SZZ-2 篩選的 PR，可能限制外部代表性。Ground truth 亦依賴 LLM 初始標註與人工驗證。
