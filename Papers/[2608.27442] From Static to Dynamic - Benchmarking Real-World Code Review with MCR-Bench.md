# From Static to Dynamic: Benchmarking Real-World Code Review with MCR-Bench

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.27442)
- 📥 [PDF](https://arxiv.org/pdf/2608.27442v1)

## 摘要（中文翻譯）

在真實軟體開發中，code review 通常透過開發者與 reviewer 的反覆互動來提升軟體品質，因此成本高且耗時。現有 LLM 自動化 code review 研究多將任務簡化為單輪、靜態決策，無法反映多輪互動及複雜問題解決過程。本文提出 MCR-Bench，首個具 defect state-aware 設計、面向真實多輪 code review 的 benchmark。資料涵蓋 Python、Java、JavaScript、TypeScript 與 C# 五種語言，共 2,269 個真實多輪 code review 任務；每項任務均標註細粒度 defect metadata，包括描述、類型與嚴重度，以及跨輪次狀態，呈現 defect 的完整演化軌跡。作者以主流 LLM 進行實驗，發現其 defect detection 與 defect lifecycle state tracking 整體能力有限，且效能會隨互動輪數增加而下降；語義複雜或低顯著性的 defect 更容易被忽略。錯誤分析進一步指出，跨輪次時間對齊失敗與長期記憶不足是重要失效機制。

## 問題背景

現有 code review benchmark 多停留在 function、diff hunk、commit 或單輪 PR 層級，通常只根據初始 PR 狀態產生一次性 feedback，忽略真實流程中的 review→revision→revalidation 迴圈。因此，既有方法無法評估模型是否能跨輪次追蹤同一 defect、判斷其由 New、Open 轉為 Resolved 或 Reopened，亦無法檢驗模型在歷史 feedback、持續 code diff 與動態上下文中的一致性。

## 解決方案

作者提出 MCR-Bench，將 code review 建模為具 PR-level context 的多輪、state-aware 評測任務。每個任務整合 Instructions、靜態 PR 資訊、linked issues，以及隨輪次變化的 code diff 和 review timeline；ground truth 則以 defect cards 表示，包含 defect description、location、taxonomy、severity 與每輪 lifecycle state。資料建構採用「先局部偵測、後全局追蹤」策略：先逐輪抽取候選 defect，再跨輪合併相同 defect 並推斷狀態轉移，最後經三次一致性篩選與具經驗開發者人工交叉驗證。

## 核心貢獻
1. 提出 MCR-Bench，將真實 PR code review 從單輪靜態任務提升為多輪、defect state-aware 的動態 benchmark，涵蓋 2,269 個任務、五種程式語言與最多十輪互動。
2. 建立結合逐輪候選偵測、跨輪 defect consolidation、lifecycle tracking、三次一致性篩選及人工交叉驗證的資料建構流程，並以 defect cards 提供描述、位置、類型、嚴重度與狀態標註。
3. 以主流商用與開源 LLM 及兩種 ACR baseline 進行評估，系統分析模型在 defect detection、生命週期狀態追蹤、互動深度、defect 特徵與 false positive／false negative 根因上的能力邊界。

## 技術方法

資料方面，作者選取 Python、Java、JavaScript、TypeScript、C# 五種語言，依 repository stars、近五年 commit 活動、issue resolution rate、貢獻者數、PR 數、授權與 fork 狀態進行篩選，最終涵蓋 38 個 GitHub repositories。PR 僅保留已 merged、修改實質程式邏輯、具有至少兩輪 commit→discussion→revision 互動，且未被 SZZ-2 判定為後續 bug-inducing 的樣本。標註分兩階段：第一階段將完整 PR 拆成各 review round，根據該輪 diff 與 comments 擷取候選 defect；第二階段彙整候選項目，進行跨輪 defect identity merging，並根據後續 commit、歷史 feedback 與 code change 推斷 New、Open、Resolved、Reopened 狀態。每項任務獨立執行三次，只有 defect 描述與狀態轉移完全一致者保留；其後由六名具五年以上經驗的開發者驗證，兩名主要 annotator 的 Cohen’s kappa 為 0.87，爭議交由第三人仲裁。評測涵蓋七個 LLM，包括 GPT-5.2、Claude-Haiku-4.5、Gemini-3-Flash、DeepSeek-V3.2、Qwen3-Max、GLM-4.7 與 Kimi-k2，另比較 PR-Agent 與 Hybrid-Review。研究評估 defect identification、lifecycle state prediction、跨輪效能變化、錯誤根因與 comment quality；提供的論文內容未報告所選最終自動評估指標及各模型的完整數值。

## 對我們的啟發
- [ ] 實務部署 code-review agent 時，不應只評估單次 comment 是否命中 defect，也應保存跨輪 defect identity、歷史 feedback 與目前狀態，避免已修復問題被重複提出或未修復問題被誤判為完成。
- [ ] 評測流程可採用與 MCR-Bench 類似的 state-aware schema，將每則 review finding 結構化為描述、位置、類型、嚴重度、狀態與證據，並分別衡量偵測能力和狀態追蹤能力。
- [ ] 對長期互動任務，應特別測試模型的 temporal alignment、歷史記憶與 reopened defect 處理能力；單輪 benchmark 的高分不能直接代表其能支援真實多輪 code review。

## 限制與未來工作

論文內容未提供各模型與 baseline 的完整數值、統計顯著性或詳細指標結果，限制了定量比較。資料集中僅納入具至少兩輪互動、已 merged 且通過篩選的 PR，可能無法代表單輪、未合併或其他協作流程。標註流程依賴 LLM 初步抽取與跨輪合併，雖有一致性篩選及人工驗證，仍可能引入標註偏差。
