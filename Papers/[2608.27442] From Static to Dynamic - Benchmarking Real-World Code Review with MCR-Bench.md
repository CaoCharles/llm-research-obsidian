# From Static to Dynamic: Benchmarking Real-World Code Review with MCR-Bench

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.27442)
- 📥 [PDF](https://arxiv.org/pdf/2608.27442v1)

## 摘要（中文翻譯）

在真實軟體開發中，code review 通常包含開發者與 reviewer 的反覆互動，以提升軟體品質，因此成本高且耗時。雖然近期研究嘗試以大型語言模型（LLM）自動化 code review，多數方法仍將其簡化為單輪、靜態的決策任務，無法呈現真實 review 的多輪互動與複雜問題解決過程。為此，作者提出 MCR-Bench，首個具備 defect state-aware 設計、用於真實多輪 code review 的 benchmark。資料涵蓋 Python、Java、JavaScript、TypeScript 與 C# 五種語言，共 2,269 個真實多輪 review tasks；每個 task 均標註細粒度 defect 資訊與跨輪狀態，包括 defect description、type、severity 及其完整演化軌跡。作者實驗發現，主流 LLM 在 defect detection 與 defect lifecycle state tracking 上整體能力有限，且輪數增加時效能顯著下降；模型對不同 defect type 與 severity 的表現差異很大，語意複雜或低顯著性的 defects 更容易被忽略。此外，錯誤分析指出跨輪時間錯位與長程記憶不足，是 false positives 與 false negatives 的重要來源。

## 問題背景

現有 code review benchmark 已從 diff-hunk 層級擴展至 PR 層級，但大多仍把 review 視為單輪、靜態的回饋生成或決策任務。這種設定忽略真實流程中的 review、revision、revalidation 循環，也無法評估模型是否能追蹤 defect 在不同輪次的 New、Open、Resolved 或 Reopened 狀態，因而不足以反映跨輪語境一致性與歷史問題驗證能力。

## 解決方案

作者提出 MCR-Bench，將 code review 建模為具備 defect lifecycle 的多輪 PR-level 評測任務。每個 task 結合固定的 PR metadata 與 linked issues，以及隨輪次變化的 code diff、review timeline 和互動歷史；ground truth 則以 defect cards 表示，包含 defect description、location、taxonomy、severity 與各輪 lifecycle state。資料建構採用「先局部偵測、後全域追蹤」策略：先逐輪擷取候選 defects，再跨輪合併同一 defect 並推導狀態轉移，最後經多次一致性篩選與人工交叉驗證，以提升標註可靠性。

## 核心貢獻
1. 提出首個以 defect state-aware 與多輪互動為核心的 PR-level code review benchmark，收錄 2,269 個跨五種程式語言的真實 tasks。
2. 建立「逐輪候選偵測、跨輪缺陷合併與 lifecycle tracking、三次一致性篩選、人工交叉驗證」的多階段資料建構流程，並取得 Cohen’s kappa 0.87 的 annotator agreement。
3. 以 defect type、severity、interaction depth 與 lifecycle state tracking 分析主流 LLM 的能力邊界，並建立 false positive 與 false negative 的細粒度失敗根因分類。

## 技術方法

MCR-Bench 涵蓋五種語言與 2,269 個真實 GitHub multi-round PR tasks。作者先依語言、repository maturity、stars、近五年活動、issue resolution rate、contributors、PR 數量、license 與 fork 狀態篩選 repositories；再保留已 merged、涉及實質程式邏輯、初始 commits 不超過 10、且存在「commit→discussion→revision」循環的 PR，並排除 bot 互動及經 SZZ-2 判定後續引入 bug 的 PR。每個 task 輸入包含 instructions、PR information、linked issues、當輪 code diff，以及截至當輪的 timeline。標註分兩階段：第一階段僅以單輪 diff 與 review comments 偵測候選 defects，以提高 recall；第二階段整合所有候選項，依完整 PR 歷史、後續 commits 與先前 feedback 進行跨輪 defect consolidation 和 lifecycle tracking。狀態包括 New、Open、Resolved、Reopened。每個 task 的 pipeline 獨立執行三次，僅保留 defect cards 與狀態轉移完全一致者；之後由六名具五年以上經驗的開發者進行人工驗證，兩名主要 annotators 的 Cohen’s kappa 為 0.87，不一致時交由第三人仲裁。實驗評估主流商用與開源 LLM，以及調整後的 PR-Agent 和 Hybrid-Review，聚焦 defect identification、state prediction、跨輪效能、錯誤根因與 comment quality。論文提供候選評估方向包括 BLEU-4、ROUGE-L、LLM Scoring 與 LLM-Hit-Judge，但提供文字未完整揭示最終選定指標及全部實驗設定。

## 對我們的啟發
- [ ] 若要部署自動 code review，評測不應只看單輪 comment generation，也應記錄每個歷史 defect 是否仍 Open、已 Resolved 或再次 Reopened。
- [ ] 實務系統可將跨輪 review comments、commits 與 defect identity 結構化保存，並在新一輪 review 時顯式提示未解決問題，以降低 defect forgetting 與 temporal misalignment。
- [ ] 模型評估應按 defect type、severity 與 review round 分層報告，而非只提供單一總分；尤其應單獨檢查低顯著性、語意複雜及安全相關缺陷的漏檢情形。

## 限制與未來工作

論文提供的文字未完整呈現所有實驗表格、模型分數、最終評估指標選擇與詳細 prompt 設定，因此無法比較各模型的量化優劣。資料主要來自符合嚴格條件的 GitHub repositories，且排除了後續被 SZZ-2 判定為引入 bug 的 merged PR，可能限制分布代表性；LLM 輔助標註也可能引入模型偏差。
