# Graph-Based Agentic AI with LangGraph: Workflow Pathways for Long-Running Stateful Business Processes

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2607.19297)
- 📥 [PDF](https://arxiv.org/pdf/2607.19297v1)

## 摘要（中文翻譯）

本文是一份實務指南，介紹以圖（graph）為基礎的 workflow pathways，支援企業流程中的長時間執行、有狀態、多步驟生成式 AI 系統。本文不把 LangGraph（用於 stateful agents 的低階 orchestration framework）視為模型品質 benchmark 的對象，而是提出三個可執行 recipe：具 repair loop 的 SQL analytics、具 evidence gating 的 agentic retrieval-augmented generation（RAG），以及具 interrupt 與 checkpoint recovery 的 human-in-the-loop（HITL）policy review。這些案例展示 typed state、conditional routing、deterministic tools、retries、interrupts、checkpoints 與 traces 如何協同運作。作者依 workflow complexity fit 定位 LangGraph，而非主張其為通用預設方案；簡單工具使用可採 ReAct 或 plain SDK loop，結構化抽取與驗證可採 schema-first tools，prompt 或 program optimization 則可採 DSPy。

## 問題背景

企業中的生成式 AI 常不是單次 prompt，而是包含工具呼叫、驗證、分支、失敗修復、長時間等待與人工核准的多步驟流程。plain SDK 或 ReAct loop 可處理簡單工具使用，但若狀態、路由與恢復邏輯留在 prompt 或應用程式巢狀控制流中，便難以檢查、測試、稽核與跨程序恢復。本文要解決的是如何判斷何時需要 LangGraph，並將這些流程需求具體組織成可執行 pathway，而非提升模型本身的品質。

## 解決方案

作者以 LangGraph 作為低階 workflow orchestration layer，透過 typed shared state、nodes、conditional edges、deterministic tools、retry/repair routes、interrupts 與 checkpoints，把原本隱含的流程控制轉化為可觀察的 state graph。核心方案包含三條 pathway：SQL analytics 將驗證與執行錯誤導向修復；agentic RAG 將 evidence quality 與 citation verification 轉為 answer、retry 或 fail-closed 路由；HITL policy review 則以 risk score 觸發 durable interrupt，保存狀態並在 reviewer feedback 後 resume。其主要創新不在新模型或新推理演算法，而在以 workflow-complexity fit 選擇 orchestration，並使路由、暫停、恢復及 audit trail 成為明確產品行為。

## 核心貢獻
1. 提出一套依工作流程需求選擇 LangGraph 或較簡單替代方案的 decision guide，明確區分 durable state、branching、repair、human review 與 prompt optimization 等問題類型。
2. 提供三個可執行且可檢查的 workflow recipes：SQL generate–validate–execute–repair、agentic RAG retrieve–grade–generate–verify，以及 HITL policy review 的 risk–interrupt–resume 流程。
3. 將 typed state、conditional edges、retry budgets、fail-closed termination、interrupt、checkpointer 與 route traces 組織為可測試、可稽核的產品流程行為，而非隱藏於模型提示中的控制邏輯。

## 技術方法

本文採 practitioner-oriented、可執行 recipe 方法，而非模型訓練或統一 benchmark。三種 workflow 均以 LangGraph StateGraph 建構，使用 TypedDict 定義共享狀態，將 user input、中間 artifact、錯誤、retry 次數、路由相關欄位與最終輸出傳遞至多個 node。SQL 路徑依序進行 schema lookup、SQL generation、validation、query execution 與 business summary；validation 或 execution error 會由 conditional edge 導向 retry、fail 或下一步。RAG 路徑先分析問題，再 retrieval、document grading、answer generation 與 citation verification；evidence_grade 或引用驗證結果決定 retry、clarify、finalize 或 failed。HITL 路徑先 draft decision、risk score，再依 risk_level 導向低風險 finalize 或 interrupt_for_review；interrupt payload 暴露 draft、風險與 policy passages，透過 Command(resume=...) 提供 reviewer feedback，並以 checkpointer 保存可恢復的 thread state。節點邊界對應 schema lookup、驗證、評分與審核等產品事件；route function 應保持小型並回傳明確標籤。評估採 focused workflow tests 與 contract assertions，檢查 retry、拒答、interrupt/resume、狀態保存與 decision record，而非答案品質指標。

## 對我們的啟發
- [ ] 若驗證失敗、證據不足或風險升高會改變下一步，應把這些條件建模為顯式 state 與 route，而不是只在 prompt 中要求模型自行處理。
- [ ] 應依任務複雜度選工具：線性工具呼叫可先用 plain SDK/ReAct，結構化輸出可優先採 schema-first，只有在持久狀態、分支、修復或人工審核是產品需求時才引入 LangGraph。
- [ ] 測試不應只檢查最終答案，也應驗證 route 與 state transition，例如 retry budget 是否生效、弱證據是否阻止 supported answer，以及 HITL resume 是否保留原始狀態並產生 decision record。

## 限制與未來工作

本文是 recipe 與設計指南，不是 empirical benchmark，未評估 production accuracy、latency、cost、model quality、streaming UX、observability、deployment topology 或框架量化比較。僅完整實作 SQL、agentic RAG 與 HITL 三條路徑；multi-agent subgraphs、customer support、跨 session memory 僅部分提及。HITL 範例使用適合本地測試的 InMemorySaver，生產環境需改用持久化 checkpointer。
