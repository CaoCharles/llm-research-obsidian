# No PUN Intended: Plausible Unknown Names for Person-Centred LLM Evaluation

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.21206)
- 📥 [PDF](https://arxiv.org/pdf/2608.21206v1)

## 摘要（中文翻譯）

人名廣泛被用作 LLM 評測中的 prompt 變數，涵蓋 factuality、privacy leakage、bias 與 abstention。然而，若未控制人名的證據狀態，測量結果可能混淆 memorisation、retrieval、name priors，以及錯誤人物歸因。本文將 unknown name 操作化定義為：具備合理的 First-Last 形式、沒有可索引的完整姓名證據，且在有文件記錄的 validation run 中沒有歧義訊號。作者提出 PUN（Plausible Unknown Names）協定，結合 Wikidata 衍生的姓名元件、具備網路存取能力的 LLM 篩選，以及受控搜尋再驗證，以建構並驗證此類名稱。研究報告 acceptance rate、reproducibility、ablation 與一項 204 人的人類研究。結果顯示，通過驗證的名稱比控制組更具 name-like 特徵，而參與者僅在 3% 的情況下找回人物證據。作者釋出 300 個名稱及其比較控制組。

## 問題背景

現有人名型 LLM 評測常直接使用真實人物名、變體名或非名稱字串，未控制完整姓名是否具有公開證據、同名者、拼寫變體或著名人物吸引效應。因此，模型產生資訊、拒答或偏見時，難以區分 memorisation、retrieval、name-conditioned priors、錯誤人物混淆與 unsupported generation。非字串或畸形輸入雖能降低人物證據，卻犧牲了真實的人名形式。

## 解決方案

作者提出 PUN（Plausible Unknown Names）協定，將 operational unknownness 定義為三項條件：候選字串是合理的兩組件 First Last 姓名；指定 validation run 找不到 exact full name 或設定的等價形式所對應的 indexed public person evidence；同時沒有近似拼寫、倒置順序、搜尋修正、著名姓名 attractor 或非人物指涉等 ambiguity signals。PUN 先從 Wikidata human entities 的 given-name 與 surname 元件組合候選，再進行格式篩選，接著以 web-enabled LLM 做廣泛 triage，最後以固定查詢模板與變體規則進行可稽核的 controlled web search。其核心創新是把姓名的證據狀態視為評測變數，並以具時間、來源與規則限制的驗證快照取代「不存在人物」的絕對宣稱。

## 核心貢獻
1. 提出 operational unknownness 的明確定義，將 plausible full-name form、無 indexed exact-name evidence 與無 full-name-level ambiguity signals 納入同一評測條件。
2. 提出可稽核的 PUN 三階段協定：Wikidata 元件生成、local format checks、web-enabled LLM triage 加 controlled web search revalidation，並報告 reproducibility 與 ablation。
3. 釋出一組 300 個 operationally unknown 名稱、300 個 public-person comparison names，以及 3,600 個 famous-name distance controls，並以 204 人研究檢驗人類可恢復性。

## 技術方法

候選生成使用 2026 年 5 月的 Wikidata dump：從 1,350 萬個 human entities 經姓名解析與出生地國家映射後，取得 417 萬筆 source pool；保留 8,404 個 given-name 元件與 30,576 個 surname 元件。作者組合兩個元件形成 First Last 字串，排除標題、suffix、非 Latin script、過長或重複形式，並要求元件出現在多筆來源記錄且具 native-language metadata；以 source-country 分層抽樣，並禁止同國重新組合。Web-facing validation 分兩階段：首先以 gpt-4.1-mini 執行「Who is {name}?」查詢，再由 gpt-5.2 adjudicator 將結果分類為 found、ambiguous、fail 或 no_info；LLM 僅作 triage，不作最終證據依據。只有 no_info 候選進入 controlled search，檢查 exact quoted/unquoted name、反轉順序、保留重音符號與 ASCII-folded 形式，以及有限的 spelling、vowel 與 phonetic variants；若結果標題、snippet、URL、knowledge panel 或頁面內容出現 person-like evidence，便判為 found 或 ambiguous。評估包含 acceptance yield、三次重跑的 end-to-end agreement、validator ablations、LSTM name model 的 bits per character（BPC）、14 個 tokenizer 的 fragments-per-character，以及 204 名參與者對姓名 plausibility、搜尋證據與 chatbot 結果的判斷。

| 十次 rerun 後仍為 no_info | 27/300 |
| LSTM median BPC：PUN／public-person | 3.16／2.45 |
| 人類認為 PUN 名稱是 plausible full name | 63.0% |

作者據此指出：PUN 名稱在字元預測性與 tokenizer fragmentation 上比非名稱控制組更 name-like；但 human search 對其找回人物證據的比例很低，且主要分歧集中於近似名稱與其他 ambiguity boundary cases。

## 對我們的啟發
- [ ] 在 biography、privacy leakage、factuality 或 abstention 評測中，應將姓名的公開證據狀態明確分層，避免把真實人物證據與模型 hallucination 或 name prior 混為一談。
- [ ] 不能只使用 exact quoted search；本文 ablation 顯示，加入 reversed、ASCII-folded、拼寫與 phonetic variants 會大幅降低錯誤接受，說明近似名稱是重要混淆來源。
- [ ] PUN 名稱不應被視為永久不存在的人，而應視為具時間、搜尋供應商、locale 與設定依賴性的 validation snapshot；正式實驗前應重新驗證，並將 stable_no_info 子集用於更保守的 negative control。

## 限制與未來工作

PUN 的 unknownness 依賴搜尋供應商、設定、locale 與時間，Hosted LLM 和搜尋索引也可能改變；無法證明現實中不存在該姓名或模型未見過它。資源限於 Latin-script、兩組件 First Last，Wikidata 來源亦不具全球人口代表性。姓名元件仍可能攜帶性別、文化、宗教、階級或族群聯想。未來應擴展至非 Latin script、不同命名制度，並量化 provider 與 locale sensitivity。
