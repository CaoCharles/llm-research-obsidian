# Specification Portability Across LLM Development Agents: Cross-Agent Compatibility in Specification-Driven Software Migration

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.21208)
- 📥 [PDF](https://arxiv.org/pdf/2608.21208v1)

## 摘要（中文翻譯）

本論文研究跨 agent 的 specification portability，探討在一個 LLM 開發環境中建立或組織的 specification，轉交另一個 agent 後，能否維持實作品質。作者以 Oracle-to-PostgreSQL migration 作為受控的 software transformation 任務，分兩階段進行實驗：第一階段在 1,006 個 PL/SQL 檔案上評估 specification-first migration pipeline，其中 623 個成功重新生成，380 個生成腳本可於 PostgreSQL 16 成功執行；第二階段使用 1,802 組 Oracle 腳本及其 PostgreSQL 實作，評估 Amazon Kiro、Google Gemini 與 GitHub Copilot 的 native 與 foreign specifications。研究採用 Token F1、exact match、SQL syntax validity、AST exact match、AST mean similarity 與 immediate runnability。結果顯示，specification 長度不足以預測實作品質，跨 agent 傳遞可能造成高度依賴 agent 的效能下降；Gemini 直接使用 Kiro-origin specification 的 replicated case 最差。Rewriting 可改善 Gemini，compression 沒有普遍效益，而 retrieval-augmented ingestion 是 Gemini 與 Copilot 兩者 Pareto frontier 的共同策略。

## 問題背景

論文要解決的是：一個 agent 產生的 operational specification，轉交異質 LLM development agent 後，是否仍能有效引導實作。既有 SDD 與 multi-agent 研究多聚焦於 specification 的用途、模型能力、協作流程或 retrieval，較少量化 specification 在不同 agent 間的可攜性。直接以規格或 prompt 生成程式，也難以區分內容品質、表示方式與 agent-specific interpretation 對結果的影響。

## 解決方案

作者提出以 cross-agent specification portability 為核心的評估框架，將實作品質建模為 specification origin、implementation agent、specification-ingestion strategy 與 task/context conditions 的函數。研究保留同一 specification，改變消費它的 implementation agent，並比較 native 與 foreign specification。對 foreign specification，作者評估 direct ingestion、agent-specific rewriting、summarization/compression，以及 retrieval-augmented ingestion。核心創新不是提出一個宣稱普遍有效的新模型，而是把 specification 視為可能具有 agent-dependent operational interpretation 的中間知識工件，並以方向性的 compatibility 與多維品質指標衡量其跨 agent 效果。

## 核心貢獻
1. 提出 specification portability 的明確研究問題與方向性 compatibility 定義，將 specification origin、implementation agent 與 ingestion strategy 納入分析。
2. 在 Oracle-to-PostgreSQL migration 上結合 specification-first pipeline 與 cross-agent transfer 實驗，並以 lexical、syntactic、structural 與 operational 指標評估 native 和 foreign specifications。
3. 比較 direct、rewritten、compressed 與 retrieval-augmented specification ingestion，指出 rewriting 的效益具有 agent dependence，且 RAG 是 Gemini 與 Copilot Pareto frontiers 的共同策略。

## 技術方法

研究分為兩個階段。Stage 1 先對 Oracle PL/SQL 進行 preprocessing 與 database-object decomposition，將來源拆成可獨立處理的物件，以減少不相關 context，並允許失敗物件單獨 regeneration。agent loop 由 application layer、agent controller、LLM 與 MCP-based tools 協作，反覆提供 messages 與 tool schemas、執行工具呼叫並回傳結果，直到完成、無更多 tool call 或達到 iteration limit；初始實作評估 GPT-oss-120b 與 GPT-o4-mini，平均每次 iteration 約 2,000 tokens、約三次迭代。Stage 2 先建立 native single-agent baseline，再固定 specification artifact、替換 implementation agent，主要系統為 Kiro、Gemini/Antigravity 與 Copilot/Spec Kit，Claude Code 與 Cursor 僅納入初始 single-agent 評估。資料包含 1,802 組 Oracle scripts 及對應 PostgreSQL scripts。評估涵蓋 Token F1、exact match、sqlglot 判定的 SQL syntax validity、AST exact match、AST mean similarity，以及在實驗資料庫中無需人工修改即可執行的 immediate runnability。RAG 設定禁止 agent 直接讀取完整 specification，改由 retrieval tools 取得相關區塊。

## 對我們的啟發
- [ ] 在 heterogeneous SDD workflow 中，不應假設 specification 是 agent-neutral；實務上應為不同 implementation agent 建立 portability smoke test 與 native/foreign quality baseline。
- [ ] 規格管理應區分穩定的語意內容與 agent-specific view；可保留共同 specification，再依 agent 以 rewriting 或選擇性 retrieval 提供實作所需區塊。
- [ ] 不能以 specification 長度或 lexical similarity 作為品質代理；部署 migration agent 時，應同時檢查 SQL syntax、AST 結構與實際執行結果，且將 immediate runnability 視為受測試 schema 限制的保守訊號。

## 限制與未來工作

研究主要系統化評估 Kiro、Gemini 與 Copilot，部分 agent 與交叉組合未執行，且 pricing constraints 限制了實驗範圍。LLM generation 具有 nondeterminism，僅部分異常結果被複現。Immediate runnability 是在空的 live database 與 generated stubs 上測試，作者明確指出它只是 lower bound。研究也未證明 RAG 普遍優於所有策略；未提供完整 adaptation 數據、統計顯著性或跨任務泛化結果。
