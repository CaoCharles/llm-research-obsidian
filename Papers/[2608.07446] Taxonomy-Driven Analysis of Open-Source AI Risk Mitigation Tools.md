# Taxonomy-Driven Analysis of Open-Source AI Risk Mitigation Tools

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.07446)
- 📥 [PDF](https://arxiv.org/pdf/2608.07446v1)

## 摘要（中文翻譯）

大型語言模型（LLM）在企業環境快速採用，帶來營運、安全與治理風險。隨著生成式 AI 從試點走向生產，人工辨識與緩解危害難以擴展。現有工具涵蓋模型評估、對抗測試、runtime guardrails 與 observability，但工具生態系仍然分散；其技術描述也未必能直接對應治理框架或風險分類。本文提出一套以 taxonomy 為驅動的分析 protocol，將 21 個開源 LLM 評估與安全工具映射至擴充版 MIT AI Risk Mitigation and Response Taxonomy 的 32 個子類別。研究使用 LLM-assisted RAG pipeline 分析原始碼與文件，並由三名 reviewer 進行驗證。Fleiss’ Kappa 為 0.509，majority vote 後 F1 score 為 75.5%。結果顯示工具主要集中於技術與營運控制，治理、法律監管及金融市場控制則大多缺乏直接支援，因此需要結合工具、組織流程與監管機制的分層風險緩解架構。

## 問題背景

企業 LLM 風險同時來自模型、prompt、retrieval pipeline、存取控制、營運監控與下游流程，但現有開源工具多針對單一工程任務，使用的技術術語難以對應治理框架與正式 risk taxonomy。既有評估也常聚焦模型或單次 benchmark，缺少跨工具、跨生命週期的風險覆蓋分析，使企業難以選擇工具、辨識能力重疊與缺口，尤其難處理治理、法律及金融層面的風險。

## 解決方案

作者提出 taxonomy-driven analysis protocol，將工具能力而非產品宣稱，映射至擴充版 MIT AI Risk Mitigation and Response Taxonomy 的 32 個子類別。核心流程是以 repository ingestion 與 RAG 輔助 LLM 擷取可驗證能力，再用嚴格 prompt 限制推論、要求程式碼 artefact 證據、逐類別記錄否定結果，最後合成完整 Tool×Risk 矩陣並由人工抽樣驗證。研究進一步提出分層 risk-mitigation architecture：以 pre-deployment evaluation、red teaming、runtime guardrails 與 observability 提供技術控制，再由組織治理、人工監督、法律及監管流程補足程式工具無法涵蓋的風險。

## 核心貢獻
1. 建立一套將開源 LLM 評估、安全、guardrails 與 observability 工具映射至 32 個 AI 風險子類別的 taxonomy-driven protocol。
2. 分析 21 個具開源性、社群採用度、維護活躍度與功能相關性的工具，形成 Tool×Risk capability matrix。
3. 以 LLM-assisted RAG 進行程式碼與文件能力擷取，再透過三名 reviewer 的抽樣驗證與 majority vote 評估映射可靠性，並提出結合技術、組織及監管流程的分層架構。

## 技術方法

研究先從 AI safety repositories、GitHub topic tags 與產業報告建立 28 個候選專案，再依開源授權、社群採用與成熟度、近期維護，以及是否屬於 LLM evaluation、runtime guardrails、adversarial red-teaming 或 observability 等條件，選出 21 個工具。資料以 2026 年 3 月的 GitHub repository 為基礎，透過 GitIngest 匯入，並排除測試檔、樣式檔、lockfile 與其他低訊號產物，保留 README、文件、原始碼、設定、backend logic、worker 與 schema 等實作證據。LLM-assisted RAG pipeline 使用 Google NotebookLM 分析各工具；三階段 prompt 包含 anchor、單工具逐 taxonomy 子類別 extraction，以及 matrix synthesis。anchor 要求 auditor persona、code-only、zero-inference、明確記錄 true negative，並區分 explicit 與 derived mapping；synthesis 以 taxonomy CSV 作為列模板、21 個工具作為欄模板，分四個 taxonomy pillar 產生完整矩陣。人工驗證採工具與類別分層的 25% 抽樣，共 168 格，由三名獨立 reviewer 判定 Yes/No，分歧以 majority vote 解決。研究使用 Fleiss’ Kappa 衡量三名 reviewer 的一致性，並以 accuracy、precision、recall 與 F1 比較 LLM 映射和人工共識。

## 關鍵結果

| 評估項目 | 結果 |
|---|---:|
| 分析工具數量 | 21 |
| Taxonomy 子類別數量 | 32 |
| Tool×Risk 矩陣儲存格 | 672 |
| 人工雙盲抽樣驗證 | 168 格（25%） |
| 人工共識標記為 Yes | 32.7%（論文提供） |
| Fleiss’ Kappa | 0.509（中度一致） |
| Accuracy | 84.5% |
| Precision | 78.4% |
| Recall | 72.7% |
| F1 Score | 75.5% |

作者指出，能力密集分布於 model safety engineering、content safety、data governance、testing 與 post-deployment monitoring；governance oversight、legal/regulatory remedies 及 financial/market controls 則大多未被程式碼層級工具涵蓋。論文未報告各工具或各 taxonomy 子類別的完整數值覆蓋率比較，也未提供與其他 mapping 方法的 baseline 對照。

## 對我們的啟發
- [ ] 企業選工具時不應只看單一產品功能，而應先以風險 taxonomy 建立 Tool×Risk coverage matrix，辨識重疊能力與未覆蓋類別。
- [ ] 對 prompt injection、內容安全、PII 防護、red teaming 與 post-deployment monitoring 等可由程式實作的控制，可組合多類工具形成生命週期式防護流程。
- [ ] 治理監督、法律救濟、金融補償與市場限制通常不是單靠開源程式即可完成，部署時仍須配置人工審查、責任分工、事件流程與監管對接。

## 限制與未來工作

研究僅分析 21 個開源工具，工具選擇受 GitHub 採用度與維護訊號影響，可能代表特定時間點的樣本。人工驗證只涵蓋 25% 矩陣，剩餘映射仍可能含誤差。NotebookLM 的 retrieval、chunking 與模型版本為封閉且不可完全控制，降低外部重現性。作者建議未來進行分層工具堆疊的情境式評估，並擴展至 proprietary tools。
