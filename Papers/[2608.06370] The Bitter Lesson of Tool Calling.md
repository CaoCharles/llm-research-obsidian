# The Bitter Lesson of Tool Calling

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.06370)
- 📥 [PDF](https://arxiv.org/pdf/2608.06370v1)

## 摘要（中文翻譯）

Tool use 使 LLM 能成為超越訓練資料、可採取外部行動的 agent；對具備程式能力的模型而言，programmatic tool calling（PTC）進一步以可自然串接及平行化的 script，取代僵化的 JSON tool calling。然而，過去尚未在既有 benchmark、當代與前代模型，以及較接近真實任務的條件下，系統評估 tools as code。本文在 BFCL v4 上比較 14 個 language models 的 PTC 與 native JSON tool calling。PTC 將工具暴露為 typed Python stubs，由模型撰寫程式呼叫，並在單一 agent turn 中執行及處理結果。結果顯示，PTC 在 14 個模型中的 11 個達到或超越 JSON baseline；GPT-5.6 家族最高提升 10.6%。在 parallel fan-out 下，13 個模型達到或超越 baseline；context rot 條件下 PTC 維持穩定，而 baseline 平均下降 2.3%。

## 問題背景

現行 agent 多以 native JSON tool calling 表達函式呼叫，但在多步串接、平行 fan-out 與長上下文下，可能面臨額外推理 turn、輸出結構限制及 schema 干擾。雖然既有研究支持以 executable code 作為 agent action，卻缺乏在標準化 function-calling benchmark 上、跨模型世代與模型家族的直接比較，因此尚不清楚 PTC 能否在維持準確率的同時改善這些情境。

## 解決方案

作者提出以 programmatic tool calling 作為 JSON tool calling 的替代介面：將每個工具 schema 編譯成 typed Python stubs，讓模型在單一 agent turn 撰寫可執行 script，以普通函式呼叫、迴圈、asyncio.gather 與 Python 狀態處理串接及平行化；subprocess 執行後由 deterministic scorer 擷取函式名稱與參數。核心創新不是新的模型架構，而是受控的 paradigm comparison，並以 chaining、fan-out、context rot 三項 ablation 檢驗 PTC 的結構性優勢與失效模式。

## 核心貢獻
1. 在 BFCL v4 的 309 筆子集上，跨 14 個、涵蓋 20 個月發布週期的模型，系統比較 PTC 與 native JSON tool calling。
2. 透過 sequential chaining、parallel fan-out 與 context rot 三項 ablation，具體分析兩種工具介面的結構性差異。
3. 指出 PTC 的可行性主要依模型世代而非模型家族分化，並揭示 JSON 在高 fan-out 下可能出現工具呼叫遺漏的結構性限制。

## 技術方法

研究在 BFCL v4 中抽取 309 筆、涵蓋 simple_python、multiple、parallel、parallel_multiple、live_simple、live_multiple、live_parallel 與 live_parallel_multiple 八類的子集，評估 14 個於 2024 年 11 月至 2026 年 7 月發布的模型，全部使用 temperature 0。兩種主要條件接收相同任務描述與函式 schema，差異僅在呼叫介面。JSON tool calling 透過 API 的 tools 參數提供 JSON function definitions，模型逐次輸出結構化 tool-call object。PTC 則在 system prompt 內嵌由 schema 生成的 typed Python stub module；模型被要求撰寫 Python script，匯入 stubs、呼叫函式並以 JSON 印出結果，agent loop 在 shell subprocess 執行，stop middleware 阻止後續推理。stubs 不連接外部服務，只回傳捕獲的函式名稱與參數。每筆資料只有當所有 ground-truth calls 都存在且參數正確才算正確；scorer 使用 deterministic normalized string comparison，移除標點並將值轉為小寫，syntax/runtime error 計零。另設 chaining（n=52、鏈長 2–20）、parallelism（n=32、fan-out 7–48，另探測 60、70、72、75、100）與 context rot（每條件 n=31、加入至 128 個含干擾 schema）的 ablation。平行任務另區分 enumeration 與 aggregation accuracy，並回報 95% Wilson confidence intervals。

## 關鍵結果

| 評估設定 | JSON tool calling | PTC | 主要觀察 |
|---|---:|---:|---|
| BFCL v4 整體（跨模型 macro mean） | 78.6% | 77.0% | PTC 在 11/14 個模型達到或超越各自 baseline；整體平均受部分模型換行編碼失敗影響 |
| GPT-5.6-Sol（BFCL v4） | 72.2% | 82.8% | 絕對提升 10.6% |
| GPT-5.6-Terra（BFCL v4） | 73.5% | 84.1% | 絕對提升 10.6% |
| Chaining（n=52，GPT-5） | 92.3% | 92.3% | 個別模型持平；Claude Sonnet 5 為 80.8%→96.2% |
| Parallelism（n=32，GPT-5） | 71.9% | 96.9% | PTC 改善 25.0 個百分點 |
| Parallelism（n=32，14 模型） | — | — | PTC 在 13/14 個模型達到或超越 baseline |
| Claude Sonnet 5 高 fan-out enumeration | N≤70 時 100%；N=72 時 75%；N=100 時 0% | N=72、100 均 100% | 顯示 JSON 的模型／序列化相關 fan-out 閾值 |
| Context rot（31 筆/條件，跨模型平均變化） | 過濾→flood：−2.3% | 過濾→flood：+5.5% | filesystem-discovery 參考條件下降 32.0% |
| Chaining latency | baseline | 13/14 模型約為 baseline 的 0.32–0.96 倍 | PTC 通常減少推理 turn；GPT-5 為 baseline 的 2.8 倍 |

論文未報告所有模型的完整 latency、成本與統計顯著性檢定；小樣本 ablation 的個別模型結果僅應視為方向性證據。

## 對我們的啟發
- [ ] 若 agent 任務包含長鏈式串接或大量獨立工具呼叫，應將 PTC 納入介面選型與 A/B 評估；論文顯示其可透過單一 script 表達多步驟與 fan-out。
- [ ] 部署 PTC 時應將程式碼格式錯誤視為獨立可靠性指標，特別是實驗中部分模型輸出字面上的「\\n」而非實際換行，導致 subprocess syntax error。
- [ ] 評估工具使用時應分離「是否確實呼叫所有工具」與「最終答案是否正確」；論文發現模型可能依賴 parametric knowledge 直接產生 aggregation answer，造成工具執行能力被高估。

## 限制與未來工作

BFCL v4 使用回傳參數的 echo-return stubs，測量重點是 argument serialization，而非真實 API 的端到端工具使用。ablation 僅 31–52 筆，個別模型信賴區間寬。benchmark ground truth 仍可能含標註噪音。PTC 具固定輸入 token overhead；論文未驗證真實服務副作用、錯誤恢復或更廣泛模型與任務。
