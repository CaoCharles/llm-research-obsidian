# The Bitter Lesson of Tool Calling

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.06370)
- 📥 [PDF](https://arxiv.org/pdf/2608.06370v1)

## 摘要（中文翻譯）

工具使用使 LLM 成為能在訓練資料之外採取行動的 agent；對具備程式能力的模型而言，programmatic tool calling（PTC）以可自然串接與平行化的 script 取代受限的 JSON tool calling。本文在 BFCL v4 上，針對 14 個不同世代的 language models，系統比較 PTC 與原生 JSON tool calling。PTC 將工具暴露為具型別的 Python stubs，由模型撰寫程式呼叫，並在單一 agent turn 中執行與取得結果。結果顯示，PTC 在 14 個模型中的 11 個達到或超越 JSON baseline；GPT-5.6 家族相對 baseline 提升 10.6%。在 parallel fan-out 條件下，PTC 在 14 個模型中的 13 個達到或超越 baseline；在 context rot 條件下，PTC 維持穩定，而 baseline 平均下降 2.3%。研究顯示，PTC 是 JSON tool calling 的可行且穩健替代方案，其表現與模型發布世代的能力相關。

## 問題背景

現有 agent 多以 JSON tool calling 呼叫 API；在多步 chaining、異質工具的平行 fan-out，以及大量無關 schemas 的 context rot 下，此介面可能增加 inference turns、限制呼叫數或造成工具遺漏。然而過去研究多聚焦 code-action agents，缺乏在標準化 function-calling benchmark 上，跨模型世代與家族直接比較 executable code 與 JSON 的系統評估。因此本文要確認 PTC 是否能在不犧牲準確率的前提下取代 JSON。

## 解決方案

作者提出 programmatic tool calling（PTC）框架：將每個工具轉為具型別的 Python stub，嵌入模型可讀的 module source；模型不再逐一輸出 JSON call，而是生成一個 Python script，於其中進行函式呼叫、順序串接、迴圈或 asyncio 平行化。agent loop 在 subprocess 執行 script，擷取輸出並以 deterministic scorer 還原工具名稱與參數。核心創新不是新的模型架構，而是以 executable、stateful、可組合的程式作為工具介面，並透過相同 benchmark、固定單回合設定與三項 ablation，量化其相對 JSON 的準確率、fan-out 能力、context robustness、延遲與 token 成本。

## 核心貢獻
1. 在 BFCL v4 的 309 個項目上，跨 14 個、涵蓋 20 個月發布週期的模型，直接比較 programmatic tool calling 與 JSON tool calling。
2. 透過 sequential chaining、parallel fan-out 與 context rot 三項 ablation，分析兩種工具介面的結構性差異與適用條件。
3. 指出 PTC 的可行性主要沿模型世代而非模型家族分化，並揭示 JSON 在高 fan-out 下可能出現工具呼叫遺漏的結構性限制。

## 技術方法

研究在 BFCL v4 中選取 309 個項目，涵蓋 simple_python、multiple、parallel、parallel_multiple、live_simple、live_multiple、live_parallel 與 live_parallel_multiple 八類，並評估 14 個模型；所有模型 temperature=0。每個項目提供自然語言 query、具型別函式集合與 ground-truth calls。JSON 條件將 schemas 經 API tools 參數提供，模型逐次輸出結構化 JSON tool-call objects。PTC 條件則把由函式 schemas 編譯而成的 typed Python stub module 嵌入 system prompt；模型撰寫 Python script，匯入 stubs 並呼叫工具，agent loop 在 shell subprocess 中執行，擷取 stdout 後由 scorer 解析函式名稱與參數。兩種主要條件均以單一模型回合完成比較，PTC 執行後由 stop middleware 終止後續 inference。工具 stub 不連接外部服務，而是回傳輸入參數。評估採 deterministic scorer，將預測與標準值轉為小寫並移除標點後進行 normalized string comparison；只有所有必要呼叫都存在且參數正確才算該項目正確，語法或 runtime error 記為零。另設 chaining 子集 n=52、parallelism 子集 n=32，以及每條件 n=31 的 context rot 子集。Chaining 測量 2–20 個 sequential calls；parallelism 測量 fan-out 7–48，並另對 Claude Sonnet 5 探測 N=60、70、72、75、100；context rot 將相關 schemas 與無關 decoys 擴充至 128 個。作者報告 accuracy、enumeration/aggregation accuracy、95% Wilson confidence intervals、延遲與 token 使用量。

## 關鍵結果

| 評估情境 | JSON tool calling | PTC | 主要觀察 |
|---|---:|---:|---|
| BFCL v4，14 模型 | 各模型 baseline | 11/14 達到或超越 baseline | GPT-5.6-Sol 與 Terra 各提升 10.6 個百分點；整體平均 JSON 78.6%，PTC 77.0% |
| Chaining，n=52 | 依模型而異 | 依模型而異 | chain length ≥12 時，PTC 相對 JSON 的絕對差距達 18.8%；GPT-4.1 因多行程式碼的 `\\n` 編碼失敗而由 98.1% 降至 40.4% |
| Parallelism，n=32 | 13/14 模型不低於 baseline | 13/14 模型達到或超越 baseline | GPT-5 由 71.9% 提升至 96.9%；PTC 在 fan-out N=100 仍維持 100% enumeration accuracy 的探測結果僅針對 Claude Sonnet 5 報告 |
| Context rot，n=31/條件 | flood 相對 filtered 平均 −2.3% | 平均 +5.5% | 128 個 schemas 的 flood 條件下，PTC 未呈現平均下降；filesystem-discovery 參考條件平均 −32.0% |
| 延遲與成本 | — | chaining 約為 baseline 的 0.32–0.96 倍（GPT-5 為 2.8 倍） | token 成本約在 fan-out N≈26 交叉；chaining 的 PTC input tokens 約為 JSON 的 1.5 倍 |

上述數字均為論文報告；小型 ablation 的單模型信賴區間較寬，作者不主張個別模型差異單獨具統計顯著性。

## 對我們的啟發
- [ ] 若 agent 任務包含長鏈式多步呼叫或大量獨立 fan-out，應評估以 typed Python stubs 和單次 script 執行取代逐次 JSON 呼叫；但需先驗證模型能穩定產生可執行的多行程式碼。
- [ ] 工具呼叫評測不應只看最終答案；平行任務應分開報告 enumeration accuracy 與 aggregation accuracy，以辨識模型是否真的執行了工具。
- [ ] 部署時需同時衡量準確率、延遲與 token 成本：PTC 在 chaining 可減少 inference turns，但有固定輸入 token overhead，且低 fan-out 時可能比 JSON 更昂貴。

## 限制與未來工作

BFCL v4 使用僅回傳參數的 echo-return stubs，因此主要測量 argument serialization，不能代表真實 API 的端到端工具使用。ablation 僅 31–52 筆，個別模型區間寬。資料標籤可能承襲 benchmark noise；此外 PTC 有固定 prompt 與輸入 token overhead。未來需在真實工具回傳值會影響後續呼叫的環境中驗證。
