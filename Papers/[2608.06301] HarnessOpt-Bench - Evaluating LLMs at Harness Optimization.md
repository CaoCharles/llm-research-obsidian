# HarnessOpt-Bench: Evaluating LLMs at Harness Optimization

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.06301)
- 📥 [PDF](https://arxiv.org/pdf/2608.06301v1)

## 摘要（中文翻譯）

隨著 LLM 日益部署於 agentic systems，其能力不僅取決於模型權重，也取決於周邊的 harness，包括 prompts、tools、control flow、memory 與 orchestration code。因此，automated harness optimization——由 AI system 依據反覆評估結果迭代改良 harness——既是提升 AI system 的重要途徑，也是對 AI system 能力的高難度考驗。然而，目前缺乏衡量 frontier LLM 執行此任務能力的共同 protocol。本文提出 HarnessOpt-Bench，評估昂貴且具 stochastic evaluation 下的 end-to-end harness optimization。optimizer 是搭配 coding harness 的 LLM，接收 target agent 的 seed harness、graded evaluation feedback 與固定 target-evaluation budget，修改 harness 並提交 final candidate；候選者依據其在搜尋期間不可接觸的 held-out test partition 上，相對 seed 的 normalized gain 評分。trusted execution environment 負責執行邊界、資源計量與版本稽核。作者在四項 downstream tasks、五個 frontier LLM、111 次 scored runs 中比較 shared 與 native harness，發現 optimizer model 的差異通常大於 coding harness，native harness 沒有穩定優勢，且增益高度依賴 task 與 seed regime。

## 問題背景

Agent 能力會受到周邊 harness 的 prompts、tools、memory、control flow 與 orchestration code 顯著影響，但現有 harness optimization 研究各自使用不同 target agents、seeds、budgets、搜尋空間與 scoring protocols，難以公平比較 optimizer model、coding harness 與方法本身。尤其 harness 改動的效果需透過昂貴且 stochastic 的 agent rollout 估計，不能以便宜、確定性的 code test 取代；若搜尋期間看得到 final evaluation，還可能把對評分的過擬合誤認為泛化改善。

## 解決方案

作者提出 HarnessOpt-Bench，將 harness optimization 定義為固定 target model、environment、verifier 與 budget 下，從 pinned seed harness 搜尋並提交可執行候選者的 end-to-end 任務。核心創新是把 normalized held-out gain 作為共同目標，將 test partition、provider credentials 與 budget enforcement 放在 optimizer 無法存取的 trusted execution boundary 之外；同時分級揭露 development traces 與 validation aggregate metrics，以兼顧診斷與選擇。框架還保存每個候選版本、隔離 target rollout、計量 token 與 case-pass 使用，並支援 shared/native harness 的 paired comparison，使模型能力、coding scaffold 與評估 protocol 能被分開研究。

## 核心貢獻
1. 提出一套受控的 HarnessOpt-Bench protocol：optimizer 在固定 seed、graded development/validation feedback 與 target-evaluation budget 下修改 executable harness，最後以不可見 test partition 上相對 seed 的 normalized gain 評分。
2. 建立 trusted、可重現且可稽核的評估基礎設施，使用不重疊的 development、validation、test splits、隔離 sandbox、模型 allow-list、token/case-pass budget 與 immutable candidate versions，降低 test leakage 與資源不公平。
3. 在四項 downstream tasks 上，以 shared coding harness 與各模型 native harness 評估五個 frontier optimizer models，並分析模型效果、harness 效果、版本進步、搜尋廣度、trace 使用與 budget 消耗。

## 技術方法

本文將 harness 視為可執行 codebase H，能修改 prompts、tool definitions、memory、control flow、context management、retrieval、answer extraction 與其他程式元件，但不可改變固定 invariants θ=(M,E,V)：target models、case environment 與 verifier。optimizer 從 pinned seed H0 開始，在 development、validation、test 三個互不重疊 partition 間搜尋。每次可提交候選 harness，或選擇 development/validation cases 執行；evaluation 回傳 aggregate score 與依 disclosure policy 提供的資訊。development 提供 case inputs、per-case outcomes 與 traces，validation 僅提供 aggregate score，test 在搜尋期間完全不可見，僅由 trusted server 對 final candidate 評估。搜尋受每個 partition 最多 100 evaluation calls、development 與 validation 各四次 full case passes，以及 target-model token cap 約束；optimizer 自身 inference 雖計量但本研究未設上限。每個 target rollout 在隔離、unprivileged sandbox 執行，model calls 經 allow-list 與 budget gateway。實驗使用 GAIA、OfficeQA、BrowseComp-Plus、Terminal-Bench 四項 tasks；五個 optimizer models——claude-opus-5、claude-sonnet-5、gpt-5.6-sol、gpt-5.6-terra、kimi-k3——分別搭配共同的 opencode 與各自 native harness，核心設計共 111 次 scored runs。seed 與 final candidate 的 held-out score 都以每個 test case 三次獨立嘗試平均。主要指標為 normalized gain g=(Eθ(H+)−Eθ(H0))/(1−Eθ(H0))；GAIA 的 seed score 為零，因此 gain 等於 raw held-out score。作者另以 task-adjusted LSS-λ 衡量 shared-harness 下的 model effect，並用 resolution band 描述重複評估噪聲，而非宣稱正式顯著性檢定。

## 對我們的啟發
- [ ] 若要比較能否改善 agent，應固定 target model、environment、verifier、seed 與 budget，並將 final evaluation 完全保留至搜尋結束；否則結果會混入 protocol、harness 或可見評分過擬合的影響。
- [ ] 實務上不宜假設模型的 native coding harness 必然較好。論文的 20 個 model-task paired comparisons 中，shared harness 勝出 11 次、native harness 勝出 9 次；GAIA 上 harness 排名還會隨 optimizer model 改變。
- [ ] 搜尋策略可優先鼓勵涵蓋多種 harness levers。論文觀察到觸及 levers 的廣度與 held-out gain 呈正相關，但此結果同時受修改總量影響，不能直接解讀為廣度本身具有因果效果。

## 限制與未來工作

論文指出此 benchmark 具 hack-resistant 而非 hackproof：固定的 development/validation feedback 仍可能讓策略利用評估器規律，未來可加入 case、tool behavior 與 verifier 的 per-run jitter。seed 複雜度未系統控制，且 GAIA stub 與成熟 seed 混合。實驗限於 Python、每項 task 一個 pinned target model，外推至其他語言、runtime、agent architecture 與 target models 尚未驗證；每個 configuration 僅兩次 optimizer replicates，也限制了變異估計。
