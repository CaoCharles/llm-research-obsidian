# HarnessOpt-Bench: Evaluating LLMs at Harness Optimization

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.06301)
- 📥 [PDF](https://arxiv.org/pdf/2608.06301v1)

## 摘要（中文翻譯）

隨著 LLM 越來越多部署於 agentic systems，其能力不僅取決於模型權重，也取決於周邊的 harness，包括 prompts、tools、control flow、memory 與 orchestration code。因此，透過自動化 harness optimization，根據評估結果反覆改進 harness，既是提升 AI systems 的重要途徑，也是衡量 AI systems 能力的高難度任務。然而，目前缺乏衡量 frontier LLM 執行此任務能力的共同 protocol。本文提出 HarnessOpt-Bench，用於評估 expensive 且 stochastic evaluation 下的 end-to-end harness optimization。Optimizer 是搭配 coding harness 的 LLM，接收 target agent 的 seed harness、分級評估回饋及固定 target-evaluation budget，修改 harness 並提交 final candidate；候選者依據其在不可存取的 held-out test partition 上，相對 seed 的 normalized gain 評分。Trusted execution environment 負責執行邊界、資源使用量測與候選版本稽核。作者在 4 個 downstream tasks、111 次評分 runs 中評估 5 個 frontier LLM，結果顯示 optimizer model 的差異通常大於 coding harness，native harness 也不一定較優，且 gains 會隨 task 與 seed regime 顯著變化。

## 問題背景

Agent 的實際能力受到 harness 顯著影響，但既有 harness optimization 研究各自使用不同 target agents、seed、budget、可修改範圍與 scoring protocol，無法公平比較 optimizer model、coding harness 或搜尋方法。更重要的是，harness 改動的效果必須透過昂貴且具隨機性的 agent rollout 估計，不能像一般程式測試般廉價驗證，因此需要同時處理失敗診斷、有限預算、噪聲辨識與 held-out generalization。

## 解決方案

作者提出 HarnessOpt-Bench，將 end-to-end harness optimization 固定成可重現、受信任執行環境中的 benchmark。Optimizer 接收 seed harness、分級 development/validation feedback 與固定預算，能編輯整個 harness codebase，最後提交候選並在搜尋全程不可見的 test split 上評分。核心創新包括以 normalized held-out gain 衡量實際改進、以 trusted server 隔離 test data 並限制 model calls、以版本化保存所有候選供稽核，以及採用 shared/native coding harness 的 paired design，分離 optimizer model 與其操作 scaffold 的影響。

## 核心貢獻
1. 提出 HarnessOpt-Bench，將 harness optimization 定義為在固定資源與 stochastic evaluation 下，從 seed harness 改進 agent 的可重現 benchmark 任務。
2. 建立含 development、validation、held-out test 分割、graded disclosure、固定預算與 trusted execution environment 的評估 protocol，以隔離 optimizer model、coding harness 與評估流程的影響。
3. 在 4 個 downstream tasks 上比較 5 個 frontier optimizer models、shared coding harness 與 native harness，並以 111 次 scored runs 證明此能力具辨識度且仍有顯著改進空間。

## 技術方法

論文把 candidate harness H 視為可執行 codebase，允許 optimizer 修改 prompts、tools、memory、control flow 與 orchestration code，但不可改變固定 invariants θ=(M,E,V)：target model、環境與 verifier。每項任務將資料切成不重疊的 development、validation、test partitions，比例分別為 20%、40%、40%。Optimizer 從 pinned seed H0 開始，在預算 B 內反覆提交候選或選擇候選進行評估；development 提供 per-case outcomes 與 traces，validation 僅提供 aggregate score，test 在搜尋期間完全不可見，直到提交 final candidate 後由 trusted server 評估。評估是 stochastic rollout，seed 與 candidate 均以每個 test case 三次嘗試的平均分數計算。核心指標為 normalized gain g=(E(H+)−E(H0))/(1−E(H0))，表示候選捕捉的 seed headroom 比例；GAIA seed 為 measured-zero，因此 gain 等於 raw score。預算主要限制為 development 與 validation 各最多 100 evaluation calls、各四次完整 case passes，以及 target-model token cap；optimizer 自身 inference 有量測但本實驗未設上限。實驗比較 5 個模型在共同 opencode harness 與各自 native harness 上的表現，涵蓋 OfficeQA、BrowseComp-Plus、Terminal-Bench 與 GAIA，共 111 次 scored runs。作者以 task-adjusted LSS-λ 分解 shared-harness 下的 model effect，並以 resolution band 描述評估噪聲；另分析 lever coverage、trace reading、修改量、token cost 與 validation-test 差距。Execution environment 使用隔離 sandbox、allow-list、token budget、不可見 test state 與 immutable candidate versioning，以支援 audit 與 reproducibility。

| 實驗規模 | 5 個 frontier optimizer models、4 個 tasks、111 次 scored runs；每個核心 configuration 執行兩次，held-out candidate 每個 test case 評估三次。 |
| Model 與 harness 效應 | 固定 task 與 harness 時，替換 optimizer model 平均改變 normalized gain 0.142；固定 task 與 model 時，替換 coding harness 平均改變 0.079，前者約為後者 1.8 倍。 |
| Shared harness 下的 LSS-λ | claude-opus-5: +0.228；claude-sonnet-5: +0.029；kimi-k3: −0.014；gpt-5.6-sol: −0.069；gpt-5.6-terra: −0.174。模型效應 resolution 為 ±0.058，細部排名仍應謹慎解讀。 |
| OfficeQA normalized gain | 最高為 claude-opus-5/opencode 0.63；最低為 gpt-5.6-terra/claude-code 0.07；任務 resolution band 為 ±0.045。 |
| BrowseComp-Plus normalized gain | 最高為 claude-opus-5/opencode 0.48；最低為 gpt-5.6-terra/codex −0.03；resolution band 為 ±0.066。 |

| GAIA normalized gain | 最高為 gpt-5.6-sol/codex 0.49；最低為 gpt-5.6-terra/mini-swe-agent 0.16；seed baseline 為 0，因此 gain 等於 raw held-out score；resolution band 為 ±0.035。 |

## 對我們的啟發
- [ ] 實務部署中，應把 prompt、工具介面、控制流程、context management 與 retry policy 視為可評估的 agent 元件，而不能只比較底層模型。
- [ ] 評估 harness optimizer 時，應保留不可見的 test partition；論文觀察到 visible validation score 多數高於最終 test score，顯示只依賴搜尋期間最佳分數可能過度樂觀。
- [ ] 搜尋策略應允許探索多種 harness levers；作者發現觸及較廣泛 levers 與 held-out gain 在四項任務皆呈正相關，但這仍是相關性而非因果證據。

## 限制與未來工作

論文指出 benchmark 具抗 exploitation 設計但並非 hackproof；固定的 development/validation feedback 仍可能讓策略利用評估器特徵。Seed harness 的成熟度未系統變化，GAIA stub 與其他 competent seeds 不可直接等同。實驗限於 Python、每項任務一個 pinned target model，且多數 configuration 僅兩次 replicate；對其他語言、runtime、agent architecture、target models 與更大規模 replication 的泛化仍未驗證。作者建議加入 cases、tool behavior 與 verifier implementation 的 per-run jitter，並建立 harness complexity ladder。
