# From Source Code to Network Profile: Automated and Traceable MUD Profile Generation for IoT Devices

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2609.31594)
- 📥 [PDF](https://arxiv.org/pdf/2609.31594v1)

## 摘要（中文翻譯）

Manufacturer Usage Description（MUD）標準允許 IoT 製造商在 MUD 檔案中描述裝置預期的網路行為，並將其轉換為可執行的存取控制政策，使遭入侵裝置只能依照製造商定義的通訊模式運作。然而，MUD 的實際採用取決於設定檔是否準確、完整且易於維護。既有流量式自動化方法需要部署裝置並長時間監控，只能捕捉觀察期間實際執行的行為，可能遺漏罕見、故障觸發或依設定而定的通訊。本文提出 AutoMUD，一個從 IoT firmware 與 software source code 自動產生可追溯 MUD profile 的工具。AutoMUD 結合 static extraction、syntactic extraction、retrieval-grounded LLM reasoning，以及 deterministic validation 與 compilation，恢復裝置的通訊行為並轉換為政策規則。每條規則都連結至 source-level provenance，未納入的發現則保留明確排除理由。實驗顯示，AutoMUD 能恢復 Linux-based repository 中的通訊行為、產生語意端點群組與結構有效的 MUD profile，並透過 semantic fault injection 支援錯誤偵測、定位、解釋與修正。

## 問題背景

論文要解決 IoT MUD profile 建置成本高、行為覆蓋不足及缺乏可維護性的問題。既有 traffic-based 方法必須部署裝置並長期監控，只能看到被實際觸發的通訊，容易遺漏罕見、條件式、更新或故障觸發行為；流量也難以說明規則對應的軟體元件、設定與執行路徑，甚至可能將收集期間的惡意行為納入政策。

## 解決方案

作者提出 AutoMUD，直接分析可遍歷的 firmware 或 software source tree，將原始碼證據轉換為可執行且可審查的 MUD profile。核心流程包括 application discovery and isolation、retrieval-oriented representation、protocol discovery、role inference、semantic endpoint consolidation 與 deterministic MUD synthesis。LLM 僅在受限 schema、檢索到的原始碼與既有證據上進行語意判讀；固定數值、符號用途、transport、角色、方向與 eligibility 則由來源證據及確定性驗證約束。每條 ACE 都保留 source-to-rule provenance，未解析或不可表示的能力不會被寬鬆轉成權限，而是輸出至 review artifacts。

## 核心貢獻
1. 提出 source-code-driven 的 AutoMUD，無需部署裝置或長期流量監控，即可從 firmware/software source artifacts 產生 MUD profile，並涵蓋罕見與條件式通訊路徑。
2. 建立從 protocol、endpoint、transport、role、direction 到 MUD ACE 的 source-to-policy synthesis 流程，對生成規則及排除能力保留可追溯 provenance 與理由。
3. 提出以 deterministic value normalization、port-use validation、transport reconciliation、eligibility checks 及 cross-artifact validation 約束 LLM，並以 semantic fault injection 展示錯誤的偵測、定位、解釋與修正。

## 技術方法

AutoMUD 首先掃描 repository，依 entry point、build target、service initializer、networking header/API 與協定詞彙辨識 application workspace，排除不可遍歷 binary，並保留 production、test、example 等 source scope。接著以不破壞函式或設定區塊的方式切分程式碼，加入路徑、行號、hash 等 deterministic metadata，透過 LLM 增補協定、函式、端點與相關性標註，再建立 application-specific vector index。Protocol discovery 同時採用 syntactic extraction 與 retrieval-grounded LLM：解析函式呼叫、欄位、macro、constant、enum 與設定；固定 port 只接受 integer literal 或純 alias chain 等可由 source 確定解析的值，避免把 sentinel、error code 或 internal discriminator 當成 port。系統以 exact-symbol search、鄰近 source context、compile-time/runtime guard 與 connection tracing 判定數值用途、啟用條件及 client/server role；connect() 支持 client，bind()/listen() 支持 server。Transport ledger 整合 TCP/UDP 證據，並要求 represented、context_only、uncertain 或 not_observed 的明確處置。最後進行 endpoint consolidation、eligibility checks、policy aggregation 與 MUD compilation，將 outbound 規則映射至 from-device-policy、inbound 規則映射至 to-device-policy。評估包含 Linux-based repository（curl、wget、OpenSSH）之 source-grounded profile recovery、結構與跨 artifact validation，以及 controlled semantic fault injection。論文未報告完整的精確率、召回率、延遲或成本等標準量化指標。

## 關鍵結果

| 評估項目 | 論文報告結果 |
|---|---|
| 分析程式碼 | Linux-based repository，包含 curl、wget 與 OpenSSH；另結合 Raspberry Pi Linux kernel source tree 的選定部分 |
| 乾淨基準 MUD | 92 個 ACEs |
| Fault injection：SSH_CHANNEL_PORT_LISTENER | 錯誤政策為 96 個 ACEs；錯誤增加 4 個 TCP/2 ACEs；修正後恢復 92 個 ACEs |
| Fault injection：SSH_CHANNEL_RPORT_LISTENER | 錯誤增加 4 個 TCP/11 ACEs；修正後恢復 92 個 ACEs |
| Fault injection：X11_BASE_PORT | 錯誤增加 8 個 TCP/6000 ACEs；修正後恢復 92 個 ACEs |
| Fault injection：PE_BAD_PORT_NUMBER | 錯誤增加 4 個 TCP/4 ACEs；修正後恢復 92 個 ACEs |
| E01 追蹤對應 | 96 個 MUD ACEs 與 96 個 traceability records 具有名稱對應；修正後保留其餘 92 個 ACEs |
| 排除項目 | 33 個 excluded endpoints 保持排除，不轉為自動政策 |
| 整體結論 | 作者稱 AutoMUD 恢復完整通訊行為、產生語意端點群組及結構有效 MUD profile；四個受控錯誤案例均可被偵測、定位、解釋並修正。論文未報告跨大量真實 IoT 裝置的完整數據比較。

## 對我們的啟發
- [ ] 對安全政策生成而言，應將 LLM 定位為受證據約束的語意解讀器，而非權限決策者；固定 port、transport 與 eligibility 應由可重現的 deterministic checks 決定。
- [ ] 應分離高召回的候選發現與保守的政策授權：不確定、動態設定或不可由 MUD 表示的能力可以保留在 review artifacts，但不應自動成為允許規則。
- [ ] 可追溯性不只是事後說明功能，也是錯誤修復機制；將 ACE、候選端點、原始碼行號、數值用途與排除理由串聯，可支援語意錯誤的局部校正並降低整份政策重建成本。

## 限制與未來工作

評估主要集中於一個 Linux-based、由 curl、wget、OpenSSH 與部分 Raspberry Pi Linux kernel source 組成的受控 repository；論文未提供大規模真實 IoT firmware、不同語言與 build system 的完整泛化結果，也未報告完整 precision、recall、執行成本或與 traffic-based baseline 的具體數值比較。AutoMUD採 best-effort 分析，動態產生、設定依賴及不可表示能力仍需人工或部署證據審查。
