# OctoLong: Mid-Training On Cross-Repository Code Contexts Enhances Long-Context Modeling

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.05141)
- 📥 [PDF](https://arxiv.org/pdf/2608.05141v1)

## 摘要（中文翻譯）

語言模型（LM）的 context length 持續增加，以支援 in-context learning、自我改進與長期 agentic workflow。然而，現有 long-context corpora 多由書籍、學術文章及 code repository 組成，資源有限，且長距離依賴通常稀疏。本文提出 OctoLong，一個結合 AST parser、language server backend 與 package manager 的 context engineering pipeline，可遞迴擷取 code references，建立長達數百萬 tokens、富含跨 repository dependencies 的 code contexts。作者以約 6.2B tokens 的 OctoLong code data，混合成約 50B tokens 的 context-extension mid-training corpus，並加入約 10B tokens 的 instruction tuning，訓練出由 600M 至 14B parameters 基礎模型衍生的 OctoLong-Instruct。與 18 個 open-weight long-context LMs 比較及透過 ablation 顯示，僅以 OctoLong 取代約 12% 傳統 context-extension corpus，即可改善 long-range retrieval、long-term state tracking、repository-level code understanding、agentic tasks，以及短 context coding 中的 API usage。

## 問題背景

現有 long-context training data 主要來自書籍、論文與單一 code repositories，雖可提供長序列，卻常缺乏跨距離、跨檔案與多跳 dependency，且部分資料來源有限、關聯鬆散或含矛盾資訊。因此模型即使支援更長 context，仍可能在 dispersed retrieval、repository-level reasoning、state tracking 與長期 agentic interaction 上表現不佳。論文要解決的是如何大規模產生高密度、可追溯且跨 repository 的長 code contexts，並驗證其對多類 long-context 能力的影響。

## 解決方案

作者提出 OctoLong context engineering pipeline，將 AST parser、language server backend 與 package manager 放入 dependency-provisioned container。對每個品質合格的 seed code，pipeline 以 tree-sitter 找出呼叫點，再透過 LSP/JEDI 執行 go-to-definition，擷取被引用的 class 或 function implementation，並以 BFS 跨 repository 遞迴展開，形成最多 128K tokens 的 dependency-rich context。作者再將約 6.2B tokens OctoLong data 以 12.05% 比例混入約 50B-token LCFT corpus，搭配約 10B-token SFT，並以 ABF RoPE 進行 32K 至 128K context extension。核心創新在於以語意與版本感知的工具鏈，將原本分散於不同 repositories 的實作依賴組合成可供 mid-training 的長序列。

## 核心貢獻
1. 提出 OctoLong pipeline，整合 AST parser、LSP backend 與 package manager，在 containerized、版本正確的 dependency environment 中遞迴擷取跨 repository 的 class 與 function implementations。
2. 收集約 6.2B tokens 的跨 repository code contexts，並建立約 50B-token 的 OctoLong-LCFT corpus 與約 10B-token 的 OctoLong-SFT mix，據此訓練 600M 至 14B 參數、支援 128K context 的模型套件。
3. 透過與 18 個 open-weight long-context LMs 的比較及三項 ablation，展示跨 repository data 對 long-context coding、general-domain long-context、agentic tool use 與 API usage 的效益。

## 技術方法

資料管線從 SEART Hub 選取至少 15 GitHub stars、超過 5 位 contributors、可安裝且宣告 dependencies 的 Python repositories；12K 個 repository 產生候選檔案，經 OpenCoder code-quality filter 後保留約 92K seeds。每個 seed 在含有正確版本 dependencies 的 containerized environment 中執行，使用 tree-sitter 索引 function calls、method calls 與 class instantiations，再透過 JEDI language server 的 GoToDeclaration 定位實作，擷取 class 或 function 邊界並以 breadth-first search 遞迴追蹤，深度上限 10，或達到 128K tokens 即停止；重複項、少於 5 層或 hop success rate 低於 60% 的 contexts 被丟棄，最終取得約 6.2B tokens。作者以 LongAttn 的 dependency attention mass 與 sink concentration 評估依賴密度及 lost-middle 現象，並以 LongPPL 的 context-sensitive key-token 比例評估資訊顯著性。模型以 Qwen3 dense base models（600M–14B）為基礎，透過 ABF RoPE 將 context 從 32K 擴至 128K，先在約 50B-token LCFT mix 上訓練，再以約 10B-token SFT mix instruction-tune；LCFT 中 OctoLong data 佔 12.05%。作者另以 1:9 比例合併 pre-LCFT 與 post-LCFT checkpoint。評估涵蓋 LooGLE V2、LongCodeQA、RepoQA、LongBench V2、OpenAI MRCR、AA-LCR、BFCL V3、τ²-Bench、LiveCodeBench V6 與 BigCodeBench Instruct Hard，並比較移除跨 repository data、移除 model merging、移除 context extension 三項 ablation。

## 對我們的啟發
- [ ] 若目標是提升 repository-level coding 或長期 tool-use，訓練資料不應只串接獨立文件；可優先建立具明確多跳 dependency、不同距離分布與低重複率的 context。
- [ ] 實務上可採用 AST、LSP 與 package manager 的聯合資料管線，而非僅依靠字串搜尋或 repository 內序列化，以取得 type- and scope-aware 的實作關聯。
- [ ] 若 context extension 可能造成 short-context regression，可參考論文的 1:9 pre-LCFT/post-LCFT model merge；但論文結果顯示此做法是其訓練 recipe 的一部分，仍需在目標模型與任務上驗證。

## 限制與未來工作

作者指出，訓練省略低資源語言資料，模型規模限制在 14B parameters，context length 限制為 128K tokens；跨 repository 遞迴擷取目前主要支援同一語言，難以處理透過 ABI 或 FFI 互動的 polyglot dependencies。未來需研究多語言 static analysis 與 control-flow tracking。
