# Vero: Can AI Agents Build Formally Verified Software Repositories?

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.13522)
- 📥 [PDF](https://arxiv.org/pdf/2608.13522v1)

## 摘要（中文翻譯）

AI agents 越來越常被用於程式設計，但通常無法保證生成程式的正確性。Verified code generation 要求 agent 同時產生 implementation 與符合 specification 的 machine-checked proof，提供更強的可信度。既有 benchmark 多聚焦個別函式，或在固定 implementation 上評估 proof generation，尚未回答 agent 能否在真實 multi-module codebase 中協調 implementation 與 proof。作者提出 Vero，首個評估 repository-level joint implementation and proof synthesis 的 benchmark，包含來自 Python、Dafny、Verus 與 Coq 的 43 個多模組 Lean 4 repository，涵蓋 cryptographic protocols、distributed systems 等領域。Vero提供 proof-only 與 code-and-proof 兩種模式，並以 formal audit 機制檢查 specification 不可滿足性及 reference code 錯誤。最強 agent 在 code-and-proof 模式僅完整解決 43 個 instance 中的 27 個，且未能解決最困難 repository 的 specifications，顯示現有 agents 距離 repository-scale verified software synthesis 仍有明顯差距。

## 問題背景

既有 verified code generation benchmark 多半只評估單一函式，或在固定 implementation 上進行 proof generation，無法衡量真實 repository 中跨模組依賴、長程推理，以及 implementation 與 proof 的相互影響。當 implementation 被修改時，可能連帶破壞其他檔案的 proofs；而 specification 或 reference code 的潛在錯誤也可能被誤判為 agent 失敗。因此需要能評估完整 codebase 一致性、同時具備實作與證明能力，並可辨識 benchmark 缺陷的 repository-level benchmark。

## 解決方案

作者提出 Vero，一個以 Lean 4 為統一驗證目標的 repository-scale benchmark。其核心是將多個 API、共享 definitions、reference implementations 與跨模組 specifications 組成完整 Lean project，並提供 proof-only 及 code-and-proof 兩種互補任務。前者隔離 proof synthesis，後者要求 agent 選擇 implementation 並證明其正確性，以直接測量兩者耦合。Vero的另一項創新是 formal audit mechanism：允許提交 machine-checked 證據，證明 reference implementation 不正確、個別 specification 不可滿足或 specifications 彼此不一致，將潛在資料錯誤轉化為可供 curator 修正的正式發現。

## 核心貢獻
1. 提出 Vero，首個在 Lean 4 repository level 評估 joint implementation and proof synthesis 的 benchmark；資料集包含 43 個多模組 instance、743 個 scored APIs 與 2,705 個 specifications。
2. 建立可由 agent 提交 machine-checked negative evidence 的 formal audit mechanism，用於發現 specification 不可滿足、reference implementation 錯誤及 specification set 不一致，協助持續修正 benchmark。
3. 以兩種 coding-agent harness、四個 frontier model configurations，在 proof-only 與 code-and-proof 模式進行完整 repository 評估，並分析 shared lemma libraries、implementation-proof coupling 與失敗類型。

## 技術方法

Vero將每個 instance 表示為多模組 Lean 4 project，固定提供 data type、helper definitions、API signatures 與形式 specifications，並以 RepoImpl 結構統一收集 API implementation。每個 specification 都是 RepoImpl→Prop，因而可在不同 implementation 上驗證，也支援 audit。資料由兩條路徑建立：Track 1 將 Dafny、Verus、Coq 等 formal repository 翻譯為 Lean 4；Track 2 將 Python repository 的 implementation 與文件、測試轉譯為 Lean，並由人工審查 specifications。每個階段由 LLM agent 執行，經 curator review、結構與 build 檢查及語意審查後才進入下一階段。Proof-only 模式提供 reference implementation，agent 只需證明全部 specifications；code-and-proof 模式則須實作所有 APIs 並證明其自身 implementation 滿足全部 specifications。Grader 從指定 marker 擷取內容，在乾淨副本重建 repository，使用 Lean toolchain 重新編譯，並透過 axiom allowlist、宣告檢測與 LLM judge 防止 axiom injection、definition edits 等 reward hacking。評估指標採 repository-level full solve：只有所有 implementation 與 specifications 均通過才算成功；實驗使用 Lean 4.29.1、90分鐘預算、兩種 coding-agent harness 與四個 frontier model configurations。另設 formal audit 路徑，接受 reference implementation 違反 specification、個別 specification 不可滿足，以及 specification set 不一致的 machine-checked evidence。

## 關鍵結果

| 評估項目 | GPT-5.5 xhigh | GPT-5.5 mid | Claude Opus 4.8 xhigh | Claude Sonnet 5 xhigh |
|---|---:|---:|---:|---:|
| Code-and-proof 完整解決數 | 27/43 | 2/43 | 8/43 | 2/43 |
| Proof-only 完整解決數 | 25/43 | 6/43 | 10/43 | 2/43 |
| GPT-5.5 xhigh code-and-proof specification 通過率 | 87.3% | 論文未報告 | 論文未報告 | 論文未報告 |
| GPT-5.5 xhigh proof-only specification 通過率 | 85.8% | 論文未報告 | 論文未報告 | 論文未報告 |

此外，10 個 instance 在兩種模式及全部八個 configuration 下皆未被完整解決。82 個 full solves 中，code-and-proof 的 helper theorem proof lines 中位數占比為 73.6%，proof-only 為 71.6%；80/82 個 full solves 的 helper 至少被兩個 specifications 共用，65/82 個至少被五個共用。

## 對我們的啟發
- [ ] 若評估目標是可信任的程式生成，應採用 repository-level 的完整通過標準，而非只統計個別 proof 或 specification 的通過率。
- [ ] Agent 工作流程應讓 implementation、proof 與 lemma-library 建構形成反覆迭代；論文觀察到 agents 往往早期固定 implementation，遇到證明困難後持續堆疊 proof，而不回頭重構較易驗證的實作。
- [ ] 正式驗證 benchmark 需要獨立的 audit 與 anti-cheating 機制；同時，code-and-proof 評估應補充 complexity 等未被 specifications 涵蓋的性質，否則 agent 可能以較低效率但較易證明的 implementation 換取完整得分。

## 限制與未來工作

Vero目前只以 Lean 4 為 target，且資料集偏向能轉譯至中等規模 Lean scaffold 的程式；並未充分涵蓋 concurrent 或 temporal protocols。benchmark 也尚未評估 incremental maintenance。formal audit 能確認形式上的 satisfiability，卻不能保證 specification 在語意上完整或正確，因此仍需人工審查與來源 formalization 交叉核對。
