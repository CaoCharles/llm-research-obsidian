# Who Grades the Agent? Privilege Separation for Coding-Agent Benchmarks

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2611.27860)
- 📥 [PDF](https://arxiv.org/pdf/2611.27860v1)

## 摘要（中文翻譯）

AI coding-agent benchmarks 是衡量與比較 LLM 能力的主要工具，但評測本身可能遭受 agent 操縱，導致未解題卻取得高分。原因在於評分通常必須執行 agent 產生的程式，而該程式可竄改測試、偽造結果或影響評分流程。作者提出 SplitBench，一個基於 privilege separation 的框架，首次將測試執行與結果判定分離：不受信任的 Evaluation environment 只執行候選程式並回傳 observation，持有 hidden expected answers 的 trusted Oracle 在外部判定分數。作者將 Terminal-Bench 2.0 與 DeepSWE v1.1 的 202 個任務轉換 180 個，與原生 grader 在 98.7% 的 agent attempts 上一致；針對可讀取 grading code 但無法取得 expected answers 的 adversarial agents，SplitBench 阻擋 75% 的攻擊，其餘多數暴露的是原始測試條件薄弱，而非 SplitBench 的缺陷。

## 問題背景

論文處理 coding-agent benchmark 的 adversarial measurement 問題：agent 不只提交解答，也可能控制執行測試與回報結果的環境，因而讀取答案、修改測試、偽造通過訊息、跨案例干擾或製造惡意證據。既有 sandbox、獨立 verifier 與事後 audit 多半仍在 agent 可控制的狀態中取得測量結果，無法由設計上保證 verdict integrity。

## 解決方案

作者提出 SplitBench，以 privilege separation 與 split verification 將工作、候選程式執行及最終判定分開。Agent 只在自己的環境中工作；框架捕捉限定 scope 內的變更，將 candidate 重播至每個案例的全新 Evaluation environment。該環境可被候選程式完全控制，但只回傳受 schema、大小與格式限制的 observation；trusted Oracle 持有 hidden data 與 expected answers，在外部比較 observation 並作出 verdict。每個案例使用新環境，並透過 relay、egress proxy 與 allowlist 管理網路存取。

## 核心貢獻
1. 提出 SplitBench，將 coding-agent benchmark 中的測試執行與結果判定分離，讓 trusted Oracle 持有 hidden expected answers，並在 agent 可控制的環境之外決定 verdict。
2. 將 Terminal-Bench 2.0 與 DeepSWE v1.1 的 202 個任務中 180 個轉換至框架，保留原始指令、環境、測試與 assertions，並以 98.7% verdict agreement 顯示轉換具有高 fidelity。
3. 以可讀取 grading code、但不能取得 expected answers 的 worst-case adversarial agents 攻擊轉換任務；429 次攻擊中 native grader 接受 230 次，而 SplitBench 未接受任何歸因於自身漏洞的攻擊。

## 技術方法

SplitBench 將評測拆成七個主要步驟：agent 完成任務；Capture environment 比對 baseline 並擷取 scope 內變更；Replay 將 candidate 套用至乾淨 baseline；每一個 test case 在獨立 Evaluation environment 中執行；adapter 接收 Oracle 釋出的 challenge、執行候選程式並回傳 observation；框架驗證 JSON schema、欄位、大小與資源界限；Oracle 以 plan 產生案例與 hidden context，再由 deterministic judge 對 evidence 判定。被測環境、adapter 與 observation 均視為不受信任，不能提供 expected answers 或自行決定正確性。候選檔案、測試案例及輸出受 manifest、檔案數與位元組數限制；active check 執行程式，passive check 僅讀取並解析檔案。每個案例完成後銷毀環境，以避免 cross-case interference；agent 的網路僅經由允許目的地的 proxy，模型請求經 relay 轉送。作者以 Terminal-Bench 2.0 全部任務與 DeepSWE v1.1 全部任務進行轉換，記錄可轉換比例、與 native grader 的 verdict agreement，以及 adversarial attempts 的接受或拒絕結果。攻擊者可讀取 grading code，但不得取得 expected answers 與隨機性；評估亦檢查 conversion fidelity、任務通過率及攻擊是否利用 SplitBench 缺陷或原始測試弱點。

## 關鍵結果

| 評估項目 | 結果 |
|---|---:|
| 可轉換任務 | 180 / 202 |
| SplitBench 與 native grader 的 attempts 一致率 | 98.7% |
| 轉換成本中位數 | 約每任務 10 美元 |
| SplitBench 阻擋 adversarial attempts | 75% |
| 測試的攻擊總數 | 429 |
| native grader 接受的攻擊 | 230 |
| SplitBench 接受、且歸因於其評測漏洞的攻擊 | 0 |
| 原始測試弱點導致的通過 | 64 次通過中的 47 次；涉及 34 個任務 |

作者另報告 agent 在 SplitBench 下的任務通過數量「約與 native grader 相當」，但未提供該比較的具體數值。未轉換任務主要需要不只檔案集合的執行狀態，或包含速度目標；完整分類數字以外的細節，論文未在提供內容中完整報告。

## 對我們的啟發
- [ ] 評測系統應將「執行候選程式」與「判定其輸出是否正確」設為不同 trust domain；測試 runner 不應自行產生或傳遞 pass/fail 作為可信證據。
- [ ] 對 agent 產出的檔案、程序與回報都應採取不受信任假設，透過限定 candidate scope、嚴格 observation schema、資源界限及每案例全新環境降低竄改面。
- [ ] 安全框架不能補救弱 acceptance conditions；應同步審查測試是否真正驗證任務目標，因為 SplitBench 會忠實繼承原始測試可接受的投機解法。

## 限制與未來工作

框架仍信任 isolation mechanism、benchmark authors、grading code 與框架元件，未涵蓋容器或 kernel escape、hardware side channel、允許服務內的濫用，以及已公開的測試與答案。作者也承認 weak acceptance conditions 不屬於框架可判定的問題；需要速度目標、持續服務或非檔案狀態的任務可能無法轉換。
