# WikiSkill: Compiling Agent Experience into Persistent Knowledge for Skill Evolution

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.27454)
- 📥 [PDF](https://arxiv.org/pdf/2608.27454v1)

## 摘要（中文翻譯）

Agent skills 將專門知識與工作流程封裝為可重用資源，以擴展 AI agent 的能力。近期研究能從 agent 經驗中自動發現 skills，使 agent 可透過互動逐步適應；然而，支援 skill 發展的洞見通常分散在各次最佳化歷史中，難以在不同迭代間系統性重用。本文提出 WikiSkill，一個讓 agent skills 與持久化 knowledge base（wiki）共同演化的框架。WikiSkill 分離原始執行經驗、累積知識與可執行 skills，持續將經驗整合至 wiki，供後續 skill 更新使用。在多個 benchmark 與模型上，WikiSkill 穩定優於現有 skill-evolution 方法，且在多數模型與 benchmark 設定中超越 no-skill baseline。研究顯示 skill evolution 能補足 model scaling；較大型模型通常能從 evolved skills 獲得更大收益，而配備 skills 的小模型也可能勝過沒有 skills 的大型模型。Evolved skills 可跨模型與模型家族轉移，且其他模型產生的 skills 有時優於自我演化的 skills。消融實驗進一步確認持久化 wiki 對有效 skill evolution 至關重要。

## 問題背景

論文要解決的是 agent 如何將多次執行中的成功策略、失敗原因與最佳化歷史，轉化為可持續重用的 procedural knowledge。既有 EvoSkill、Trace2Skill 與 SkillOpt 雖能分析 traces、保留提案歷史或整合經驗，但沒有獨立且持續演化的知識表示層，導致洞見分散、失敗提案可能重複，後續迭代難以累積跨輪次的根因分析與證據。

## 解決方案

WikiSkill 在 raw execution traces 與 executable skills 之間加入持久化 wiki layer，形成 Raw、Wiki、Skills 三層架構。Inference Agent 使用目前 skills 執行 training rollouts；Wiki Maintainer 從成功與失敗 traces 進行 root-cause analysis，建立或修訂 pattern pages、index 與 evolution log；Skill Proposer 讀取 wiki、歷史 skill-impact 記錄及按需檢視 traces，提出單一 skill 的建立或 patch 更新；Gating and Rollback 再以 validation performance 決定接受或回復 skill。核心創新是 skill 可回滾，但 wiki 永不回滾，因而累積 rejected proposals、重複錯誤與成功證據，支援後續 refinement 與跨模型移植。

## 核心貢獻
1. 提出 WikiSkill 三層知識架構，將 immutable raw traces、持久化且累積的 wiki，以及可執行 skills 明確分離，讓經驗能被結構化保存並供後續 skill evolution 使用。
2. 在五個 benchmark 與五個模型上系統比較 WikiSkill、Trace2Skill、EvoSkill、SkillOpt 與 no-skill baseline；WikiSkill 在所有模型的五任務平均表現最高，且多數模型—資料集組合優於 no-skill。
3. 系統研究 skill evolution 與模型能力及跨模型轉移的關係，證明 skills 可補足模型規模差距、跨模型家族轉移，並透過消融與案例研究確認 persistent wiki 對持續 refinement 的重要性。

## 技術方法

問題設定將資料集分為互斥的 training、validation 與 testing splits；agent π 配備工具 U 與 active skill set S，執行任務後產生包含 observations、actions、tool calls、工具輸出及最終答案的 trajectory，並以 domain-specific scoring function 計算平均表現。每輪先由 Inference Agent 只讀取 skills、不可讀取 wiki，於 training set 產生 immutable raw traces。Wiki Maintainer 從分層抽樣的成功與失敗 traces 中提取成功策略、失敗模式與根因，對 wiki/patterns 進行 patch-based 更新，並寫入 logs.md。Skill Proposer 以 ReAct 方式先讀取 wiki index、skill-impact.md 和整體 pass/fail 摘要，再透過 read_file 按需選取 pattern pages 與 raw traces，建立或修改一個 skill；skills 以 SKILL.md 儲存程序，PURPOSE.md 連結其來源 pattern。候選 skill 於 validation split 評估，只有當分數嚴格高於目前最佳值才接受，否則回復 skills；wiki 則保留所有紀錄。最終在 unseen test split 以 accuracy 或 benchmark-specific score 評估。實驗涵蓋 LiveMath、SealQA、SpreadSheetBench、OfficeQA 與 ALFWorld，使用 Qwen-3.5-4B/9B、Qwen-3.6-27B、Gemma-4-31B 與 Gemini-3.5-Flash，並與 no skill、Trace2Skill、EvoSkill、SkillOpt 比較；每種方法重複三次，報告平均 test performance，並以 paired bootstrap testing 檢驗差異。

## 關鍵結果

主要結果如下；數值為五個 benchmark 的平均 test performance（%），除非另有說明。

| 模型 | No skill | 最佳既有方法 | WikiSkill | WikiSkill 相對 No skill |
|---|---:|---:|---:|---:|
| Qwen-3.5-4B | 26.2 | 35.2 | 38.5 | +12.3
| Qwen-3.5-9B | 29.9 | 42.3 | 47.4 | +17.5
| Qwen-3.6-27B | 39.4 | 53.3 | 63.3 | +23.9
| Gemma-4-31B | 41.3 | 49.1 | 54.9 | +13.6
| Gemini-3.5-Flash | 49.5 | 56.1 | 68.1 | +18.6

| 具體比較 | 結果 |
|---|---|
| Qwen-3.5-9B WikiSkill vs Qwen-3.6-27B No skill | 47.4% vs 39.4% |
| Qwen-3.6-27B 在 SpreadSheetBench | 40.8% → 81.7%（WikiSkill，+40.9） |
| Gemini-3.5-Flash 在 LiveMath | 33.0% → 72.6% |
| Gemini-3.5-Flash 在 SpreadSheetBench | 50.5% → 76.6% |
| Qwen-3.6-27B 在 ALFWorld | 52.8% → 77.6% |
| Qwen-3.5-9B 使用 Qwen-3.6-27B skill 的 ALFWorld | 70.2%，高於自我演化的 63.4% |

消融實驗使用 Gemini-3.5-Flash：Inference Agent 不讀 wiki、Skill Proposer 讀 wiki 的預設設定平均為 63.7%；兩者皆不讀 wiki 時為 48.7%，顯示持久化知識帶來 +15.0 個百分點。若讓 Inference Agent 在 training rollout 期間讀取 wiki，平均降至 60.9%，支持作者對訓練 traces 資訊價值下降的解釋。

## 對我們的啟發
- [ ] 若要建立可長期運作的 agent learning pipeline，應將原始 traces、可執行策略與診斷知識分層保存；即使某次 skill patch 被拒絕，其失敗原因與驗證結果仍應保留，避免後續重複嘗試。
- [ ] 訓練 rollout 與知識整理應分離：本文結果顯示 Inference Agent 在演化期間直接讀取 wiki 反而降低平均表現，因此可讓 rollout 只使用正式 skills，再由維護器分析 traces。
- [ ] 跨模型部署 skills 前應進行 target-model validation。論文中的 transfer 可能大幅提升表現，也可能產生 negative transfer，例如 Qwen-3.5-4B skill 使 Gemini-3.5-Flash 的 SpreadSheetBench 從 50.5% 降至 18.1%；技能內容需區分可泛化程序與模型特定 workaround。

## 限制與未來工作

論文的評估主要集中於五個 benchmark、五個模型與 filesystem-based skill，且 skill 以完整內容注入 system prompt，未研究 skill retrieval 或 triggering 失敗。WikiSkill 每輪需額外的 Wiki Maintainer 與 ReAct Proposer LLM 呼叫，成本可能較高；文中雖比較呼叫複雜度，但未提供完整金錢成本、延遲或能耗數字。另未充分驗證長期部署中的 wiki 規模膨脹、錯誤知識累積與跨任務泛化。
