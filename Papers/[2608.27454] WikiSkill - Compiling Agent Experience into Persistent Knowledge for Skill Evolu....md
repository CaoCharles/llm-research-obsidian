# WikiSkill: Compiling Agent Experience into Persistent Knowledge for Skill Evolution

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.27454)
- 📥 [PDF](https://arxiv.org/pdf/2608.27454v1)

## 摘要（中文翻譯）

Agent skills 將專門知識與工作流程封裝為可重複使用的資源，以擴展 AI agent 能力。近期研究可從 agent 經驗中自動發現 skills，使 agent 能透過互動逐步適應；然而，指導 skill 開發的洞見通常散落在最佳化歷史中，限制了跨迭代的系統性重用。本文提出 WikiSkill，一個讓 agent skills 與持久化 knowledge base（wiki）共同演化的 framework。WikiSkill 分離 raw execution experience、累積知識與可執行 skills，並持續將經驗整合至 wiki，供後續 skill 更新使用。在多個 benchmark 與 model 上，WikiSkill 穩定勝過現有 skill-evolution 方法，且在大多數 model-benchmark 設定中優於 no-skill baseline。結果顯示，skill evolution 與 model scaling 互補；較大模型通常能從 evolved skills 獲得更多收益，而具備 skills 的小模型可大幅超越沒有 skills 的更大模型。Evolved skills 也能跨模型與 model family 有效轉移，甚至其他模型演化出的 skills 可能優於 self-evolved skills。消融實驗確認，持久化 wiki 的知識累積是有效 skill evolution 的關鍵。

## 問題背景

論文處理 LLM agent 如何從執行經驗中持續發展可重用的 procedural skills。既有 EvoSkill、Trace2Skill 與 SkillOpt 雖會保存歷史提案、從 trajectories 萃取教訓或使用 rejected-edit feedback，但沒有獨立且持續演化的知識表示；重要洞見因而散落於 traces、skill proposals 與評估歷史，難以跨迭代整合、避免重犯錯誤並支持長期 skill refinement。

## 解決方案

作者提出 WikiSkill，於 raw execution traces 與 executable skills 之間加入 persistent Wiki Layer，形成 Raw、Wiki、Skills 三層架構。每輪由 Inference Agent 執行 rollout，Wiki Maintainer 對成功與失敗 traces 做 root-cause analysis 並累積 patterns，Skill Proposer 以 wiki、近期 traces 與歷史影響紀錄提出單一 skill 更新，最後透過 validation gating 接受或 rollback。核心創新在於 skill 可回滾，但 wiki 永不重置，並以 evolution log 與 skill-impact tracker 保存證據、拒絕歷史及接受結果，讓後續提案建立在編譯後的持久知識上。

## 核心貢獻
1. 提出 WikiSkill 三層知識架構，將 immutable raw traces、持久化且累積的 wiki 知識，以及可執行 skills 明確分離，並以 Wiki Maintainer、Skill Proposer 與 validation gating 組成持續演化迴圈。
2. 在五個跨領域 benchmark 與五個模型上進行系統評估，WikiSkill 的平均表現均高於 no-skill baseline 與所比較的既有 skill-evolution 方法；消融結果支持 persistent knowledge accumulation 的關鍵作用。
3. 系統研究 skill evolution 與模型規模及跨模型轉移的關係，顯示 skills 可補償模型規模差距、跨 model family 轉移，且 skill discovery 與 skill execution 是可區分的能力。

## 技術方法

問題設定將資料集分為 disjoint 的 training、validation 與 testing splits；agent π 使用工具 U 與目前 skill set S 執行多步 trajectories，並以 domain-specific scoring function 計算平均表現。WikiSkill 從 (S0,W0)=(∅,∅) 開始。每個 iteration 中，Inference Agent 只讀取 active skills，於 training set 產生包含 reasoning、tool calls、觀察與答案的 immutable raw traces；系統抽樣成功及失敗 traces。Wiki Maintainer 讀取既有 wiki 與抽樣 traces，建立或 patch patterns/index.md，並更新 evolution log。Skill Proposer 以 ReAct 多輪方式先讀 wiki index、skill-impact.md，再按需讀取 pattern pages 與 raw traces，提出建立或 patch 單一 skill 的 atomic proposal。候選 skill set 在 validation split 評估；只有當分數嚴格高於目前最佳 validation score 才接受，否則 rollback skills，但 wiki 與提案結果仍保留。skills 的完整內容在 inference 時直接注入 system prompt，以排除 triggering 或 retrieval failure。實驗涵蓋 LiveMath、SealQA、SpreadSheetBench、OfficeQA、ALFWorld 五個 benchmark，以及 Qwen-3.5-4B、Qwen-3.5-9B、Qwen-3.6-27B、Gemma-4-31B、Gemini-3.5-Flash 五個模型；每方法完整 evolution 執行三次，報告平均 test performance，並以 paired bootstrap testing（1,000 iterations，p<0.05）檢驗差異。

## 關鍵結果

主要結果如下；分數為五個 benchmark 的平均 test performance（%）。

| 模型 | No skill | 最佳既有方法 | WikiSkill | WikiSkill 相對 No skill |
|---|---:|---:|---:|---:|
| Qwen-3.5-4B | 26.2 | 35.2 | 38.5 | +12.3 |
| Qwen-3.5-9B | 29.9 | 42.3 | 47.4 | +17.5 |
| Qwen-3.6-27B | 39.4 | 53.3 | 63.3 | +23.9 |
| Gemma-4-31B | 41.3 | 49.1 | 54.9 | +13.6 |
| Gemini-3.5-Flash | 49.5 | 56.1 | 68.1 | +18.6 |

WikiSkill 在五個模型區塊的平均表現皆為最高；相較各模型最強競爭方法，提升分別為 3.3、5.1、10.0、5.8、12.0 個百分點。代表性單項結果包括 Gemini-3.5-Flash 在 LiveMath 由 33.0% 提升至 72.6%，在 SpreadSheet 由 50.5% 提升至 76.6%；Qwen-3.6-27B 在 ALFWorld 由 52.8% 提升至 77.6%。Qwen-3.5-9B 使用 WikiSkill 的平均 47.4% 高於 Qwen-3.6-27B no-skill 的 39.4%。跨模型轉移亦有效：Qwen-3.5-9B 使用 Qwen-3.6-27B 演化的 skill，在 ALFWorld 達 70.2%，高於 self-evolved skill 的 63.4%；但存在 negative transfer，例如 Qwen-3.5-4B skill 使 Gemini-3.5-Flash 的 SpreadSheet 由 50.5% 降至 18.1%。Gemini 消融實驗中，Inference Agent 無 wiki access 時，Skill Proposer 有 wiki access 的平均分數為 63.7%，無 persistent wiki 時為 48.7%；讓 Inference Agent 也讀 wiki 則降至 60.9%。

## 對我們的啟發
- [ ] 若要建立長期 self-improving agent，不應只保存最新 skill 或提案；應另外維護可搜尋的 pattern catalog、演化日誌與接受/拒絕影響追蹤，讓後續更新能利用累積證據並避免重複失敗。
- [ ] 訓練 rollout 與 skill 維護應分離知識存取權限：論文的設定是 Inference Agent 只讀 skills，而 Wiki Maintainer 與 Skill Proposer 讀 wiki；讓執行 agent 直接讀 wiki 反而可能產生較不具資訊量的 traces。
- [ ] 跨模型部署 skills 前應檢查其抽象層次與執行能力。一般程序可正向轉移，但針對小模型的低階 workaround 或冗餘操作可能限制強模型並造成 negative transfer，因此需要 target-model validation。

## 限制與未來工作

實驗僅涵蓋五個 benchmark、五個模型與三次獨立 evolution runs；論文未在所提供內容中證明更廣泛的真實世界任務、更多模型或長期部署下的穩定性。Skill 與 wiki 由 LLM agents 維護，仍可能受 traces 抽樣、提示設計與額外推論成本影響；跨模型轉移也可能出現明顯 negative transfer。
