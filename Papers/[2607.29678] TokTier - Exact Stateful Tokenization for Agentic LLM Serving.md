# TokTier: Exact Stateful Tokenization for Agentic LLM Serving

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2607.29678)
- 📥 [PDF](https://arxiv.org/pdf/2607.29678v1)

## 摘要（中文翻譯）

LLM serving 系統會快取 prompt 的 KV state，但多數前端每次仍須對完整 request text 重新 tokenization。對 coding agent 而言，長 transcript 只追加少量 tool result，卻可能因 token boundary 改變而無法直接重用。TokTier 是具 stateful 的 tokenization service，保證輸出 token IDs 始終與完整 reference tokenizer 一致。session continuation 會針對 append 周邊小視窗重新 tokenization，經 per-request stable-boundary check 後才 splice；失敗則擴大視窗或完整重算。無可重用 prefix 的請求則以 run-local rules 在 GPU 執行 exact pre-tokenization 與 BPE，並以 shadow verifier 抽樣驗證。涵蓋 17 個 tokenizer families 的測試均無 divergence；incremental repair 為 0.5–1.1 ms，GPU 可在 0.87 ms 編碼 1M 字元請求，接入 vLLM 後 TTFT 中位數降低 16–34%。

## 問題背景

現有 LLM serving 雖能以 prefix/KV cache 跳過模型端的 cached prefill，前端仍在每次呼叫掃描並 tokenization 完整 transcript。coding agent 常只追加約 1.4K 字元，卻重算 86K–123K tokens；長期累積成 O(N²) 工作。直接串接舊 token IDs 與新 token IDs 又不正確，因 append 可能改變 pre-tokenization boundary 及 BPE merges。固定 overlap heuristic 沒有 correctness guarantee，而無 reusable prefix 的大型 rebuild 又造成 CPU latency tail。

## 解決方案

TokTier 將 workload 分成 session continuation 與 state miss 兩條路徑，並以「輸出 token IDs 必須等同完整 reference tokenization」作為唯一 contract。continuation 保存 token IDs、byte spans 與 tokenizer hash，只重算 append 加舊文尾端視窗；藉由 matched run 與 family-specific stable-boundary certificate 決定是否 splice，任何不確定性都擴大視窗或 fallback。對大型 state miss，作者將 GPT-family sequential regex 轉換為 run-local、可平行的字元分類與 piece-start predicates，接上 GPU BPE。CPU reference path 處理小請求、未支援 family 與例外，另以 sampled shadow verifier 監控線上 divergence。

## 核心貢獻
1. 刻畫 coding-agent 的 session-level tokenization workload：153,951 次呼叫中，多數請求只追加少量文字，少數 session initialization 或 rebuild 卻攜帶達百萬 token 的完整上下文。
2. 提出具 exactness contract 的 stateful incremental repair：保存 token IDs 與 byte spans，僅重算 append 周邊視窗，並以 tokenizer-family-specific stable boundary certificate 保證安全 splice，失敗時退回更大視窗或 reference full tokenization。
3. 提出 GPT-family pre-tokenization 的 run decomposition 與 GPU BPE pipeline，並建立結合形式化分析、差分測試、real-text sweep、agent replay 與 runtime shadow verification 的完整驗證方法。

## 技術方法

TokTier 位於 request router 與 model engine 之間，以 content hash 綁定 tokenizer configuration、vocabulary、merge table 與 normalization 規則。router 先查找具相同 tokenizer version 且文字 prefix 相符的 session state；state hit 時保存的 token IDs、byte spans 與文字索引被用於 incremental repair。系統取舊文字末端 w=512 字元加 append，以 reference-compatible engine 重算，對比 cached 與 fresh token records，尋找位置與 ID 均一致的 run；只有在 run 至少含兩個 token、覆蓋字元數超過最長詞彙 token，且包含 family-specific stable/asynchronizing boundary certificate 時才 splice。檢查失敗便將視窗加倍，最多五次，最後 full retokenization。state miss 的大型請求則把 GPT-family regex pre-tokenization 改寫成 character-class maximal runs、run summaries、bounded lookback 與 per-character piece-start predicate，再在 GPU 以 size-specialized kernels 執行 BPE；小請求、unsupported family、normalization 或 backpressure 則走 reference CPU。評估涵蓋 17 個 tokenizer families、synthetic/adversarial inputs、12.4 TB real-text corpus、93,000+ agent replays、15,000 edits 與 vLLM 0.25 serving。指標包括 token-ID 與 piece-boundary divergence、單請求 P50/P99 latency、GB/s、TTFT、burst capacity、GPU/CPU contention 與 shadow verification mismatch。

## 關鍵結果

| 評估項目 | TokTier 結果 | 對照或條件 |
|---|---:|---|
| 差分 split checks | 1.50×10^10，0 divergence | 17 個 production tokenizer families；另有 12.4 TB real-text corpus sweep |
| End-to-end GPU checks | 6.21×10^7，0 divergence | 6 個 production tokenizers |
| Incremental repair | 0.5–1.1 ms | context 100K–3M 字元；最高較 HF 快 437× |
| Cache-based baseline | 1M 字元時 TokTier 快 2.1× | 與 fully prewarmed Gigatoken 比較 |
| GPU full tokenization | 1M 字元 0.87 ms | 最高較 HF 快 491×，較最快已發表 CPU 方法快 23.4× |
| vLLM TTFT | 中位數降低 16–34%；P99 降低 23% | loaded regimes 與 recorded burst arrivals |
| 服務容量 | 1,821 requests/s | 4 個 repair cores + 1 GPU、P99 目標 50 ms；16-core stateless front end 為 40 requests/s |
| 正確性驗證 | 93,000+ replayed agent steps，0 divergence | 另測 15,000 adversarial edits；unsupported 或失敗案例走 fallback |

## 對我們的啟發
- [ ] 在 agent serving 中，KV-cache hit rate 高並不代表前端成本低；應將 tokenization state 視為與 KV state 分離、可具有更長 TTL 的服務層狀態。
- [ ] 任何跨請求 token reuse 都不應只依賴固定 overlap 或相同 token ID run；實務上應採用可證明的 boundary certificate，並設計 fail-safe fallback 以確保錯誤只增加成本、不改變輸出。
- [ ] 評估 tokenizer 優化時應同時測量 incremental continuation、large state miss、burst P99、TTFT 與容量，而不能只比較離線吞吐量；GPU path 還需驗證單請求同步與 host contention。

## 限制與未來工作

GPU full-tokenization path目前只涵蓋 cl100k、o200k 與 DeepSeek pattern families，部分 normalization、added-token handling、byte spans 與 unsupported tokenizer 仍需 CPU 或 fallback。兩個 tokenizer families 不符合 repair predicate。大型 append 的平行修復、cache engine 與 GPU span export仍屬 prototype，尚未通過完整 admission battery；runtime shadow verification亦是抽樣而非全量。
