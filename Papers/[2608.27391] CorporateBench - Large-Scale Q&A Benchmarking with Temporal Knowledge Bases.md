# CorporateBench: Large-Scale Q&A Benchmarking with Temporal Knowledge Bases

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.27391)
- 📥 [PDF](https://arxiv.org/pdf/2608.27391v1)

## 摘要（中文翻譯）

大型語言模型（LLM）日益能夠回答企業級文件集合中的複雜問題，但評估仍然困難：企業不願公開內部通信資料，而合成資料集又過於簡單。本文提出 CorporateBench（CB），一個經人工驗證的多任務問答 benchmark，其規模接近 LLM 在企業通信網路中可能面對的條件，評估語料超過 230,000 份文件。CB 從資訊抽取與 knowledge base querying 兩個面向評估 LLM，涵蓋四家由合成生成的公司，員工數從 12 人至 10,000 人不等。每個語料庫皆由描述一致世界的時間演化 knowledge base 取樣而成，因此即使跨越數十萬份文件，也能維持跨文件邏輯一致性。作者評估五個 LLM，發現當輸入規模接近真實企業尺度時，模型表現日益下降。CB 因而提供企業通信推理的評估指標，補足現有 benchmarking 生態的重要缺口。

## 問題背景

現有 long-context 與企業 benchmark 無法充分衡量 LLM 在大規模、互相連結且具時間變化的企業文件上進行檢索、抽取與推理的能力。needle-in-a-haystack 類測試過度簡化；真實企業資料又受 NDA 限制，難以公開；既有企業資料集通常規模小、資料來源不夠企業化，或由 LLM 直接生成而缺乏可驗證且全域一致的 ground truth。因此，模型可能在短文件或單文件問答表現良好，卻無法處理企業級跨文件關係與時間推理。

## 解決方案

作者提出 CorporateBench，以 procedurally generated、temporally evolving knowledge bases 作為企業世界的唯一真實來源，再由 KB 生成具角色約束、時間順序與關係證據的企業通信文件。框架先建立包含公司、部門、團隊、員工、專案、任務與會議的 ontology 和關係圖，模擬一季工作與會議活動，再生成可任意擴展的 email 與 meeting 文件。QA 標籤直接由經驗證的 SPARQL 查詢從 KB 計算，而非由 LLM 產生；同時提供 RAG 與直接 KB/SQL 兩種設定，以區分文件檢索瓶頸和結構化查詢推理能力。

## 核心貢獻
1. 提出 CorporateBench，一個涵蓋 12 至 10,210 名員工、總計 263,466 份文件的企業級多任務 Q&A benchmark。
2. 建立以 temporal knowledge base 為核心的資料生成流程，透過 ontology、角色約束、時間關係與證據字串維持跨文件邏輯一致性，並可產生任意規模語料。
3. 將資訊抽取與 knowledge base querying 分離，提供 KB evaluation、topic classification、KB/Topic/Integrated QA，以及 RAG 與直接 KB 查詢對照，揭示規模增大時的關係、時間與檢索瓶頸。

## 技術方法

資料建構分為 KB 建立、企業模擬、文件生成與驗證。公司以 Turtle/OWL ontology 表示，包含 Company、Department、Team、Employee、Project、Task、Meeting 等實體，以及 WorksOn、ReportsTo、MemberOf、WorksAt、Attends、Organize、BelongsTo 等關係。作者依公司規模建立階層，模擬 90 天任務、六類會議，季度末加入約 10% 新員工並標記關係的起訖時間；再以 Claude Haiku 4.5 為實體產生屬性、別名及 email 內容。文件透過預定義的 3,217 個關係證據字串保證關係可被揭示，並以格式、主題、人格與正式程度增加詞彙多樣性。資料涵蓋四家公司，共 263,466 份文件。任務包括 KB 關係/實體抽取、主題分類，以及 KB QA、Topic QA 和 Integrated QA。QA 問題由 250 個人工撰寫模板搭配 KB 的 verified SPARQL 查詢產生；答案類型包括字串、日期、整數、布林值與集合。RAG 使用 pgvector 與 text-embedding-3-small，KB 設定則提供 SQL 工具。實體與關係抽取採 Precision、Recall、F1；主題分類採 macro-F1；QA 多數採 exact match，集合答案採 F1。另從完整語料抽取 100 封 email，經 Claude Sonnet 4 反轉證據生成正負樣本，由 50 名非專業評閱者完成 1,000 次判斷。

## 關鍵結果

主要結果如下（數值為論文報告的 F1；表中 RAG/KB 分別表示文件檢索與直接結構化 KB 查詢）：

| 評估面向 | 主要觀察與數據 |
|---|---|
| 語料規模 | 四家公司分別有 354、3,926、26,493、232,693 份文件，總計 263,466 份；每題文件數約由 1.4 增至約 931。 |
| KB 實體抽取 | 各模型跨規模 F1 約 0.715–0.824，整體比關係抽取穩定。XL：Haiku 0.766、GPT-5 Nano 0.777、Gemini 2.5 Flash Lite 0.715。 |
| KB 關係抽取 | 隨規模明顯下降。最佳 F1 由 S 的 0.845 降至 XL 的 0.494；XL：Haiku 0.494、GPT-5 Nano 0.206、Gemini 0.205。 |
| 時間關係抽取 | 最困難；最佳 F1 由 S 的 0.470 降至 XL 的 0.173。XL：Haiku 0.173、GPT-5 Nano 0.062、Gemini 0.128。 |
| RAG KB QA | 各規模最佳分數為 S 0.527、M 0.501、L 0.312、XL 0.269；最佳模型均為 GPT-5 Nano（S/M）或 GPT-5.1（L/XL）。 |
| KB KB QA | 各規模最佳分數為 S 0.767、M 0.742、L 0.628、XL 0.642，均由 Claude Sonnet 4.5 達成。 |
| RAG Topic QA | 各規模最佳分數為 S 0.672、M 0.564、L 0.423、XL 0.492。 |
| KB Topic QA | 各規模最佳分數為 S 0.848、M 0.687、L 0.576、XL 0.571，均由 Claude Sonnet 4.5 達成。 |
| Integrated QA | RAG 最佳分數為 S 0.511、M 0.564、L 0.560、XL 0.566；KB 最佳分數為 S 0.611、M 0.640、L 0.653、XL 0.647。 |
| 人工驗證 | 評閱者正確判斷文件是否明確主張目標關係的比例為 76.2%（1,000 次判斷）。 |
| 主題分類 | Biocure 上 LLM 以 50 個 few-shot examples 達 0.877–0.982，Pound 上為 0.598–0.751；Pound 的 TF-IDF+LR 在 100K 訓練樣本達 0.983。 |

整體而言，直接 KB 存取通常優於 RAG，且 KB–RAG 的 KB QA 差距由 S 的 0.24 擴大至 XL 的 0.37；但 Integrated QA 隨規模略有改善，作者將其歸因於較大型語料提供更豐富的跨來源脈絡。

## 對我們的啟發
- [ ] 企業 RAG 評估不應只測單文件命中率，應加入需要跨大量文件整合、時間判斷與關係鏈追蹤的問題，並以語料規模曲線觀察效能衰退。
- [ ] 直接 KB 查詢明顯優於 RAG，顯示部署優化不能只依賴更長 context；應結合結構化索引、關係抽取、時間有效性管理與可驗證查詢。
- [ ] 應分開評估 entity extraction、relationship extraction、temporal extraction 與最終 QA，因為實體辨識相對穩定，但關係錯誤與時間錯誤會在企業級文件量下累積並造成級聯影響。

## 限制與未來工作

資料主要是 email，未涵蓋 Slack、Teams、技術規格、財務報告、試算表與簡報。企業演化只模擬 90 天，未呈現併購、策略轉向與多年制度性知識累積。文件由 Claude Haiku 4.5 生成，可能帶有固定文風與模型偏差；人工驗證僅抽樣 100 封，且非專業評閱者正確率為 76.2%。
