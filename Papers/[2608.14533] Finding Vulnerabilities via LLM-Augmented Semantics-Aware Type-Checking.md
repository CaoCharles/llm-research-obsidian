# Finding Vulnerabilities via LLM-Augmented Semantics-Aware Type-Checking

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.14533)
- 📥 [PDF](https://arxiv.org/pdf/2608.14533v1)

## 摘要（中文翻譯）

傳統的軟體漏洞偵測通常依賴安全專家將不安全的程式模式編碼為演算法規則，但這類方法多聚焦於語法模式，忽略變數與函式名稱所包含的深層語意。隨著軟體系統日益複雜，僅使用語法規則建模漏洞更加困難。本文提出具語意感知的漏洞偵測方法，設計可直接由原始碼中符號與表達式的自然語言意義推導出的 SETYPE semantics-aware type system。在 SETYPE 中，語意型別推論與型別檢查皆由 Large Language Models (LLMs) 執行，型別檢查失敗則表示可能存在漏洞。作者實作 PYSETYPE，展示其在 Python web applications 中的可行性；於真實應用程式上達到 87% detection precision 與 88% detection accuracy，並發現 15 個潛在 zero-day vulnerabilities，其中 9 個獲開發者確認。

## 問題背景

現有 static analysis 多依賴人工撰寫、建構於 AST、CFG 或 PDG 上的 syntactic rules，難以完整表達變數與函式的語意、外部函式行為及多樣化的 sanitization。規則維護成本高，也容易在提高 recall 時引入大量 false positives。直接讓 LLM 閱讀整個 codebase 又受限於 context、跨檔案依賴與長程推理，因此需要兼具程式探索覆蓋率與語意理解能力的分析框架。

## 解決方案

作者提出 SETYPE，將漏洞條件視為一種 semantic type mismatch：變數與表達式被賦予如「由使用者提供的檔案路徑」等自然語言型別，操作則定義其所需的語意型別。PYSETYPE 將此方法整合進 pytype，以確定性的 CFG 與 bytecode traversal 探索程式，再在局部操作中呼叫 LLM 執行 SETYPE inference、unification、branch-context tracking 與 vulnerability checking。其核心創新是以 LLM 直接處理程式語意，而非要求 LLM 產生完整靜態分析規則，同時透過 CWE checklist、taint analysis 與既有 syntactic analysis 約束推理範圍。

## 核心貢獻
1. 提出 SETYPE，一種以自然語言語意型別描述變數與表達式，並以 LLM 執行型別推論及檢查的漏洞偵測方法。
2. 實作 PYSETYPE，將 SETYPE 整合至 pytype，透過 CFG、bytecode-level execution traversal、syntactic types 與 LLM semantic reasoning 分析 Python web applications。
3. 在 SVEN、近期 CVE 及 103 個熱門開源專案上進行評估；SVEN 上達到 87% precision、87% recall、88% accuracy 與 87% F1，並報告 15 個潛在漏洞，其中 9 個獲開發團隊確認。

## 技術方法

PYSETYPE 建立在 pytype 2024.10.11 之上，使用 Qwen3 32B，透過 Ollama API 執行，top-p 設為 0.3，其餘參數採預設值。首先以 pytype 分析 dependencies，產生 interface stubs、per-file object maps 與 CFG；再辨識 main function 及 Flask、FastAPI、Django 的 web endpoints。之後以延伸的 pytype virtual machine 在 bytecode 層級模擬 execution flow，沿 CFG 探索可達基本區塊，並追蹤 syntactic type、SETYPE 與每個區塊的 execution context。SETYPE 是由變數名稱、函式名稱、comments、docstrings 及操作上下文形成的自然語言語意型別。對 assignment、function call、branch、merge 與 loop 等操作，系統使用 zero-shot prompt 要求 LLM 推論或更新型別；分支合併與迴圈則由 LLM 彙整不同路徑的語意。漏洞偵測針對外部函式呼叫套用 CWE-based rules，並以 checklist 分別檢查來源、操作及 sanitization 條件；若 SETYPE 與預期操作型別不匹配，便提出潛在漏洞。系統亦使用 taint analysis 追蹤外部輸入，以減少不必要的 LLM 查詢。評估使用 precision、recall、accuracy、F1，並與 CodeQL、Bandit、VulnHuntr 比較。

## 關鍵結果

論文在 SVEN 上比較四種工具，結果如下：

| Tool | Precision | Recall | Accuracy | F1 Score |
|---|---:|---:|---:|---:|
| CodeQL | 0.67 | 0.39 | 0.83 | 0.49 |
| Bandit | 0.75 | 0.84 | 0.70 | 0.79 |
| VulnHuntr | 0.52 | 0.45 | 0.53 | 0.48 |
| PYSETYPE | 0.87 | 0.87 | 0.88 | 0.87 |

SVEN 經篩選後包含 27 個 repositories 的 80 個 vulnerability instances，並以 vulnerable 與 patched 版本共 160 個程式版本評估。PYSETYPE 另分析 103 個熱門 Python 專案，發現 15 個潛在 zero-day vulnerabilities，其中 9 個獲開發者確認。最大 codebase 包含 195 個 API endpoints 與 26k Python bytecodes，分析約需 14 小時，估計 LLM inference cost 為 3.19 美元。近期 CVE 資料集包含 9 個 CVEs、14 個 program versions；論文未在提供文字中報告該資料集的完整 precision、recall、accuracy 或 F1 數值。

## 對我們的啟發
- [ ] 將 LLM 限制在約 200 tokens 的局部語意推論，並由確定性的 CFG traversal 負責程式探索，可作為結合符號分析與 LLM 的實務設計模式。
- [ ] 自然語言中的變數名稱、註解與 docstrings 能補充傳統 AST、CFG 與 data-flow analysis 未直接表達的意圖；實務部署時可將其作為 taint analysis 與 vulnerability rules 的語意補強。
- [ ] 漏洞規則仍可採 checklist 形式拆解，例如同時檢查檔案存取、外部輸入來源與 sanitization，藉此降低單次 LLM 判斷的複雜度；但工具輸出仍應交由開發者確認。

## 限制與未來工作

作者指出 PYSETYPE 繼承傳統 static analysis 的限制，包括 imprecise point-to analysis；同時也有 LLM inference cost、非決定性與語意推論錯誤。實作僅支援 Python 3.10、Flask、FastAPI、Django，且對 inheritance interactions 的處理不完整，可能造成分析遺漏。論文未提供完整的模型消融、跨語言評估或所有資料集的詳細統計。
