# Tytan: Interactive Neurosymbolic Construction of Analytic Semantic Schemas from Relational Data

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.06331)
- 📥 [PDF](https://arxiv.org/pdf/2608.06331v1)

## 摘要（中文翻譯）

從自然語言查詢介面到自動報告生成，資料分析工具都需要資料描述：其中包含哪些真實世界實體、哪些欄位是度量或識別碼，以及資料表如何連接成分析單位。目前 semantic layer 通常由人工撰寫，形成知識取得瓶頸，限制分析系統擴展，使非技術使用者依賴專家，且本身容易出錯。本文提出 TYTAN，一個可從 relational database 及可選的簡短使用者描述，自動建構 analytic semantic schema 的系統。TYTAN 結合資料庫 symbolic analysis 與 LLM-based semantic inference，用於提出實體、指定欄位角色與命名；當證據不足以消除歧義時，會向使用者提出針對性的自然語言問題。在七個具參考 schema 的資料域中，TYTAN 對所有實體、屬性與可聚合特徵達成 100% coverage，1,678/1,678 個自生成 retrieval claims 均可正確執行，semantic roles 與參考結果的一致率為 92–100%。在無宣告 keys 的十資料表 FIFA World Cup 2026 blind test 中，TYTAN 恢復完整 entity structure，並滿足五位獨立盲測標註者所有可滿足的期待。

## 問題背景

Relational database 通常只描述 tables、columns 與少量 constraints，缺乏實體意義、分析角色、識別碼與跨表 join 語意，導致自然語言查詢與報告系統難以可靠規劃分析。人工建立 semantic layer 成本高、難擴展且容易過時；純 symbolic methods 不理解欄位語意，純 LLM methods 則可能 hallucinate columns、keys 或 joins，且多步驟結果不一致。

## 解決方案

作者提出 TYTAN，一個結合 symbolic database analysis、LLM semantic inference 與 human-in-the-loop clarification 的 neurosymbolic pipeline。LLM 從資料表名稱、型別、樣本值與可選描述推論 entities、attributes、analytic roles、命名及關係；deterministic procedures 則驗證欄位存在性、value overlap、key uniqueness、型別證據與 join 可執行性。所有內容最後組成 ring，提供已驗證的 entity ids、分析角色、表間路徑、aggregable attributes 與自然語言 surface forms。核心創新是把資料庫 instance 作為每項語意推論的 grounding，並在證據不足時以針對性問題交由使用者裁決。

## 核心貢獻
1. 將 analytic schema construction 定義為一項獨立任務，要求 schema 同時支援分析查詢規劃、驗證與自然語言結果描述。
2. 提出 TYTAN interactive neurosymbolic pipeline，讓 LLM 負責語意推論，並以 value overlap、key uniqueness、欄位型別與可執行性等 deterministic checks 驗證每項提案。
3. 提出涵蓋 coverage、retrieval correctness 與 characterization accuracy 的 functional evaluation framework，並在七個 reference domains 與一個 blind database 上進行評估。

## 技術方法

TYTAN 輸入 relational database instance 與可選的一句資料描述，輸出稱為 ring 的受 schema 約束 JSON semantic catalog。第一階段進行 structural profiling，收集 tables、columns、declared primary/foreign keys、cardinalities、null rates、storage types 與 distinct samples；CSV/Excel 也會先載入 relational store。第二階段由 LLM 根據結構證據提出 entities、attributes、analytic roles、名稱與可能 joins，再將概念映射至實際 tables/columns。對未指派 tables，系統分類為 entity、link table、passthrough lookup 或 technical table；未指派 columns 則加入既有 entity，形成 iterative coverage sweep。第三階段驗證關係：undeclared join 必須有 value overlap，並通過 key-role guards、Numeric measure 排除、reference uniqueness 與多重候選限制，最後由 LLM 依名稱、型別和 sample values 判斷語意 plausibility。Entity id 只有在 non-null 且全表 unique 時才驗證接受，亦搜尋 composite keys；無法驗證的 junction table 不提升為 entity。欄位同時記錄 storage type 與 analytic role，避免把數字形式的 zip code、ID 或電話號碼誤當 Numeric measure。LLM 產生的 names、descriptions、reference templates 會被 deterministic cleanup，樣本值不得由 LLM 虛構。若 table role、column mapping 或 analytic type 無法由證據決定，系統提出 targeted clarification question，使用者回答後局部重建 schema。評估分為：以 expert-corrected references 比較 entity/attribute/aggregable coverage；執行 ring 內的 ID uniqueness、attribute mapping、join-chain execution 與 reference resolution 以測 retrieval correctness；再以 references 與 blind expectation suites 評估 characterization 與語意覆蓋。

## 對我們的啟發
- [ ] 對需要自動產生 semantic layer 的資料產品，應採取「LLM 提案、資料庫驗證」的分工，而非讓 LLM 直接產生不可檢查的 schema。
- [ ] 評估資料理解系統時，不應只比較欄位名稱或 schema 結構相似度；應執行實際 retrieval instructions，檢查 keys、欄位映射與 join paths 是否真的可用。
- [ ] 對 enrollment 或 link table 等依使用情境而定的結構，加入 targeted clarification loop 比強迫系統採用單一固定分類更能處理語意歧義；同時應保留 conservative defaults 以支援無人工輸入的流程。

## 限制與未來工作

目前 parallel joins 之間的 path search 在計算 aggregable attributes 時只遍歷其中一條，相關擴充留待未來工作。部分 key 選擇曾因計算時間耗盡或缺乏真實 key 而失敗，雖由一般化 guards 修正。評估資料集僅八個，且 downstream analytic correctness 未被直接評估；blind 測試中的 LLM annotators 也可能與生成器存在模型家族偏差。
