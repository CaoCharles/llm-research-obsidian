# EnSI-RAG: Entity-Structure-Indexed Retrieval-Augmented Generation for Long-Document Question Answering

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2608.21252)
- 📥 [PDF](https://arxiv.org/pdf/2608.21252v1)

## 摘要（中文翻譯）

在長篇、彼此連結的文件上進行問答仍然具有挑戰性，因為相關證據可能分散於多個實體及其關係之間。現有 Retrieval-Augmented Generation（RAG）方法通常將文件切成原始 chunks，再以 embedding similarity 進行檢索；當 chunk 邊界將實體與支持證據分開，或問題需要跨語料庫進行 multi-hop reasoning 時，效能便會下降。本文提出 EnSI-RAG（Entity-Structure-Indexed Retrieval-Augmented Generation），建立與查詢無關、以實體為中心的索引。每筆記錄 ⟨e,t,k,v⟩ 表示實體、實體類型、屬於 property、relation 或 aspect 的語義類別，以及其值，並保留通往原始來源段落的連結。查詢時，這些記錄作為 retrieval handles，由 LLM 將取回的段落整合為最終答案。此設計將證據定位與答案生成分離，同時保留可追溯的來源證據。在 Loong 與 Oolong 上，EnSI-RAG 平均準確率為 78.24，較所採用的已發表 baseline 參考分數高 6.62 分，顯示其在不同設定下的有效性。

## 問題背景

論文處理長文件與多文件集合中的 QA，尤其是證據分散於不同實體、表格列、文件或關係鏈的情境。固定長度 chunk 容易切開實體及其支持證據，也可能將無關主題混在同一檢索單位；單純 lexical 或 dense similarity 因而只能找到局部相似內容，遺漏低詞彙重疊但語義必要的證據。大型 context window 亦無法保證模型可靠利用中間位置資訊或完成跨文件聚合與 multi-hop reasoning。

## 解決方案

作者提出 EnSI-RAG，將文件先轉換為語義自洽、以單一主要實體為中心的 passages，再從每個 passage 擷取實體、類型、property、relation 與 aspect 等結構化資訊，建立與查詢無關的索引：[entity][entity type][property|relation|aspect:value] → {psg_id}。結構化記錄只負責提供檢索入口，不取代原始證據或承擔完整推理；檢索後仍回傳原始 passages，由 LLM 根據這些可追溯內容產生答案。其核心創新是以語義結構取代機械式 chunk 邊界，並在傳統 chunk-based RAG 與 fully structured QA 之間取得折衷。

## 核心貢獻
1. 提出以主要實體為中心、具語義包含性的 passage representation，取代固定長度 chunk，降低證據碎片化與無關內容污染。
2. 建立 query-independent entity-structure index，以 entity、entity type、property、relation、aspect 與 value 作為結構化 retrieval handles，並保留對原始 passages 的來源連結。
3. 提出將結構化證據定位與 LLM 答案 synthesis 分離的統一 RAG 流程，使結構化記錄輔助檢索，而由原始文件證據支撐最終回答。

## 技術方法

EnSI-RAG 分為 offline preprocessing 與 online QA。離線階段首先進行 Passage Construction：依文件結構與任務需求建立語義包含的 passage，保留來源文件、offset、標題、表頭、年份或引用等輕量脈絡，並配置穩定的 psg_id。接著進行 Information Extraction，對每個 passage 產生記錄 r=⟨e,t,M,psg_id⟩；M 由 ⟨c,k,v⟩ 欄位組成，其中 c 分為 property、relation、aspect，且每個欄位必須有局部 passage 證據支持。Index Entry Building 將欄位映射為 [e][t][c:k=v]→{psg_id}，可保留同一 key 下的重複、互補或矛盾 passages，必要時建立反向 relation entries。線上階段由 LLM 將問題轉成 retrieval plan H(q)，每個 hop 可指定 entity、type、category、field、value 或 target entity；以各欄位相容度的加權總和 score(h,x)=Σλₐsₐ(h,x) 排序 index keys，再聯集其 passage IDs、去重並可重新排序。多跳問題可使用前一 hop 發現的中間實體啟動下一 hop。最後，LLM 僅以問題、檢索到的 records 與原始 passages 生成答案。評估使用 Loong（177 題）與 Oolong-Synth（192 題）；Loong 採官方 average accuracy，Oolong 非數值題使用 LLM-as-a-judge，數值聚合題使用官方 deviation-based metric。

## 關鍵結果

主要結果如下（baseline 分數取自 SLIDERS 論文；Loong 子集可能不同，因此並非完全受控的 head-to-head 比較）：

| 方法 | Oolong | Loong | 平均 |
|---|---:|---:|---:|
| RAG | 11.32 | 54.35 | 32.84 |
| LongRAG | 22.00 | 59.10 | 40.55 |
| GraphRAG | 22.00 | 61.28 | 41.64 |
| BaseModel（GPT-4.1） | 45.56 | 76.74 | 61.15 |
| DocETL | 49.00 | 75.03 | 62.02 |
| RLM | 51.42 | 72.64 | 62.03 |
| SLIDERS | 64.67 | 78.57 | 71.62 |
| **EnSI-RAG** | **71.84** | **84.64** | **78.24** |

EnSI-RAG 相較 SLIDERS 的平均分數高 6.62 分；Oolong 高 7.17 分，Loong 高 6.07 分。消融實驗顯示：Financial 題目採 row-level passage 得分 100.00，高於 table-level 的 91.50；property/aspect 使用 coarse labels 時，English Financial 由 92.00 升至 93.50、Paper 由 88.00 升至 91.50，但 Legal 由 71.25 降至 68.75。Financial 子集的 retrieval depth 以 Top-5 最佳（94.00），高於 Top-12（92.00）與 Top-15（92.50），但主要實驗仍統一採 Top-12。效率方面，平均每 query 的總成本為 163,146 input tokens、494.30 秒與 34.35 次 LLM calls，其中離線 passage construction 與 information extraction 佔 157,031 tokens、468.51 秒及 32.35 次 calls；線上 retrieval 與 generation 分別為 19.01 秒、6.73 秒。

## 對我們的啟發
- [ ] 在表格型或高度結構化文件中，應優先依語義單位（例如財務表格列）切分，而不是只依 token 長度切分；但 passage granularity 應透過同一資料子集的消融實驗決定。
- [ ] 索引可採取結構化 metadata 定位、原文 passage 驗證與生成的兩階段設計，避免抽取錯誤直接成為模型推理事實，並提升答案 provenance 與可審計性。
- [ ] 檢索數量與標籤粒度不一定越大越好：Financial 子集 Top-5 優於 Top-12/15，且 coarse labels 對 Financial、Paper 有益但傷害 Legal，顯示 domain-specific tuning 與控制上下文干擾十分重要。

## 限制與未來工作

論文的 baseline 多取自 SLIDERS，且 Loong 評估子集可能不同，故跨方法比較缺乏完全一致的受控性。每個 EnSI-RAG 設定僅執行一次，未提供標準差或統計顯著性。離線 preprocessing 成本很高，依賴 LLM 進行 passage construction 與 extraction；Oolong 僅評估 Oolong-Synth，未涵蓋 Oolong-Real。索引品質、實體消歧與抽取錯誤的獨立分析亦仍有限。
