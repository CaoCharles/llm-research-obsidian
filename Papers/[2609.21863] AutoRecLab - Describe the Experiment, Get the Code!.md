# AutoRecLab: Describe the Experiment, Get the Code!

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2609.21863)
- 📥 [PDF](https://arxiv.org/pdf/2609.21863v1)

## 摘要（中文翻譯）

實證評估是推薦系統（RecSys）研究的核心，但將實驗設計轉換為可執行程式碼，通常仍是手動且容易出錯的工作。本文提出 AutoRecLab，一個以 Python 建置的自主 RecSys 實驗室，可根據自然語言提示自動執行推薦系統實驗。給定研究想法後，AutoRecLab 會推導明確的實驗需求、建立並驗證原型，再逐步擴充至所要求的完整實驗。其工作流程結合 retrieval-augmented generation（RAG）文件查詢、靜態型別驗證與 execution-steered tree search。在示範中，AutoRecLab 自主實作了 explicit-to-implicit feedback conversion 研究；針對六種演算法與三個資料集的 baseline 比較，九次執行中有八次成功，使用 GPT-5.4-mini 時每次平均成本約為 1 美元。

## 問題背景

論文要解決的是：研究者如何將自然語言描述的 RecSys 實驗設計，可靠地轉換成可執行、可檢查且可重現的程式碼。現有一般型 LLM 或科學研究代理可能產生 RecSys 函式庫的錯誤 API，也未必保留資料過濾、資料切分、候選集合、評估方式與 random seed 等會影響結果的實驗選擇。既有代理在 RecSys 任務上曾出現程式錯誤與方法不正確問題，因此僅能執行不等於實驗具科學意義。

## 解決方案

作者提出開源 Python 命令列工具 AutoRecLab，作為推薦演算法與實驗函式庫之上的研究自動化層。系統先把自然語言 prompt 轉為 prototype requirements 與 full requirements，再以小型原型驗證資料載入、演算法、指標與流程，最後逐步擴充至完整研究。核心創新包括：利用 RAG/MCP 查詢 OmniRec、LensKit 與 RecBole 文件以降低 API 幻覺；以靜態型別檢查和實際執行回饋修正程式；以及以 execution-steered tree search 搜尋候選實作。每個階段都保存程式碼、圖表、執行紀錄與中間狀態，供研究者檢查。

## 核心貢獻
1. 提出 AutoRecLab，一個專為推薦系統實驗設計的開源自然語言到可執行程式碼工具，涵蓋需求推導、程式生成、執行、評估與 refinement。
2. 設計 prototype-to-full 的分階段工作流程，結合 RecSys 文件的 RAG/MCP、靜態型別驗證、實際執行回饋與 execution-steered tree search。
3. 以 explicit-to-implicit feedback、資料集過濾及 random-seed splitting 等離線 RecSys 情境進行概念驗證，報告九次 baseline 執行中八次產生被分類為 bug-free 的程式與圖表。

## 技術方法

AutoRecLab 的流程分為三階段。第一是 requirements engineering：LLM 根據研究 prompt 產生兩組需求，prototype requirements 通常只包含一個資料集、一個 baseline 演算法與一個 cutoff，以降低初始執行成本；full requirements 則保留使用者指定的完整演算法、資料集、指標與視覺化內容。第二是 prototyping：系統透過 OmniRec 執行生成的 Python 程式；OmniRec 提供資料載入與訓練執行層，連接 RecPack、RecBole、LensKit 與 Elliot，並支援超過 230 個資料集。生成候選程式後，系統使用 MCP 存取索引文件與程式碼，進行靜態型別檢查，並在獨立 workspace 執行。LLM 依據 console output 與程式結果，逐項判定需求是否滿足，以及候選程式是否 buggy；需求滿足比例定義為節點分數 S，範圍為 0 至 1。候選實作形成搜尋樹，節點選擇先在 buggy 與 bug-free 集合間取樣，再透過 epsilon-greedy 選擇最高分或隨機候選，直到 S=1 或達到迭代上限。第三是 refinement：從可執行原型逐步增加完整需求，每次修改後重新執行與評估。示範研究比較 explicit-to-implicit feedback 的不同 binarization thresholds，並報告 NDCG@10 與 Precision@10；論文未提供更完整的資料切分細節或各演算法的數值結果。

## 對我們的啟發
- [ ] 若將自然語言研究問題轉為逐項、可檢查的實驗需求，可提升實驗流程的可追蹤性；實務部署時仍應讓研究者審閱資料切分、負回饋轉換、候選集合與評估指標。
- [ ] 先執行小型 prototype 再擴充完整實驗，有助於在高成本執行前發現 API、型別與流程錯誤；這種設計可作為研究代理的工程化檢查點。
- [ ] 需求覆蓋率、程式可執行與 bug-free 分類不等同於科學正確性，因此實務上應增加獨立的結果合理性、方法學一致性與可重現性審查。

## 限制與未來工作

研究僅涵蓋有限且相對簡單的離線 RecSys 任務，且部分可執行分析仍缺乏科學意義。系統受 OmniRec、底層 LLM、文件索引範圍與序列式搜尋限制，可能產生較長執行時間。作者未完整評估程式碼品質、不同 LLM 或更複雜任務；未來將擴充函式庫與任務、平行化 tree search，並加入文獻搜尋與論文撰寫。
