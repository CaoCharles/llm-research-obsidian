# CodePoisonRAG: Knowledge Poisoning Attacks on Retrieval-Augmented Code Generation

## 連結
- 📄 [arXiv](https://arxiv.org/abs/2609.02774)
- 📥 [PDF](https://arxiv.org/pdf/2609.02774v1)

## 摘要（中文翻譯）

Retrieval-Augmented Code Generation（RACG）透過檢索外部程式碼、文件與修補程式來提升 LLM 軟體開發能力，但也形成新的信任邊界：被投毒的知識條目可能在不修改 LLM 的情況下影響生成程式碼。過去研究主要選取既有漏洞範例，提升 RACG 輸出的整體漏洞率，尚未回答黑箱攻擊者能否建構單一、符合任務的條目，以傳播指定弱點。本文提出 CodePoisonRAG，將良性修補程式轉換為投毒條目，結合 CWE-specific Vulnerability Injection 與 Semantic Mislabeling：前者嵌入指定的 source-to-sink 流，後者加入虛假的安全聲明但不修復漏洞。攻擊者不需存取受害者知識庫、retriever、re-ranker、generator、prompt 或防禦機制，每個預期任務最多注入一個條目。作者建立涵蓋 Java 與 C、十種 CWE 的 85 個投毒條目，總投毒比例為 0.7%。三個生成器中，全部條目均進入對應查詢的 Top-3，未防禦時攻擊成功率為 0.80–0.93；面對 CodeGuarder 時仍達 0.40–0.71，顯示 RACG 投毒可針對性地建構並傳播攻擊者選定的弱點。

## 問題背景

論文關注 RACG 對外部知識庫的依賴所引入的供應鏈信任風險。既有研究可藉由選取語料庫中已存在的漏洞範例，提高生成程式的整體漏洞率，但無法同時控制預期功能、漏洞類別與任務匹配度；不匹配的範例可能無法被檢索或模仿。因此，尚缺乏一種黑箱、低投毒比例、每個任務僅使用單一條目，且能使生成結果產生指定 CWE 的攻擊方法。

## 解決方案

作者提出 CodePoisonRAG，一種針對 RACG 的 upstream targeted knowledge-poisoning framework。攻擊者先針對預期的良性程式設計任務選擇相容 CWE，再將原本安全的 fixed-code entry 修改為保留原功能、API、識別字與結構的漏洞版本。其核心攻擊鏈包含兩階段：Vulnerability Injection 修改 source–passthrough–sink 資料流，植入指定 CWE；Semantic Mislabeling 則在註解或文件加入「已完成安全處理」等虛假聲明，讓條目看似安全並提高對安全導向查詢的語義匹配。此設計同時追求檢索成功與漏洞傳播，且不依賴受害 RACG 系統的內部資訊。

## 核心貢獻
1. 提出黑箱 upstream RACG 投毒威脅模型：攻擊者不存取受害者知識庫、retriever、re-ranker、generator、prompt 或防禦機制，且每個預期任務最多注入一個條目。
2. 設計由 CWE-specific Vulnerability Injection 與 Semantic Mislabeling 組成的程式碼攻擊鏈，在維持任務對齊的同時植入指定 source-to-sink 漏洞並加入虛假安全聲明。
3. 建立涵蓋 Java、C 與十種 CWE 的 85 個投毒資料，並在三個開放權重生成器及 CodeGuarder 防禦下驗證檢索與端到端攻擊效果。

## 技術方法

RACG 流程由外部知識庫、dense retriever、可選的 re-ranker 與 LLM generator 組成。作者以 12,053 個 ReposVul fixed-code entries 建立良性檢索池，另製作 85 個 function-level poisoned snippets，包含 65 個 Java 與 20 個 C 條目，涵蓋 CWE-20、22、78、79、89、94、119、120、502、918。每個攻擊樣本從任務匹配的良性條目出發，先選擇可在既有資料流中實現的 CWE，再以 source→passthrough→sink 形式替換或修改安全操作，例如以 filename.trim() 取代路徑限制、以 sprintf 取代 snprintf，最後加入 CWE-specific 的虛假安全註解。資料庫使用 jina-embeddings-v3、1,024 維向量與 FAISS exact cosine search，候選結果再由 jina-reranker-v2-base-multilingual 重排序。生成器為 Qwen 3.5 9B、Code Llama 13B 與 DeepSeek-Coder-V2 16B，採 temperature 0 的 greedy decoding；另以 GLM-5.1 作為獨立 LLM judge，依 CWE-specific source-to-sink 規則檢查主要程式碼區塊。評估指標包括 Retrieval Success Rate（RSR）、需同時滿足檢索與漏洞生成的 Attack Success Rate（ASR）、不要求投毒條目被檢索的 Target Weakness Rate（TWR），以及 CodeBLEU。實驗比較 non-defense、benign counterpart 與 CodeGuarder 防禦情境。

## 對我們的啟發
- [ ] RACG 的安全邊界不只在模型與 prompt，也包括資料匯入、公共程式碼來源、版本更新與知識庫建立流程；實務上應對外部條目進行來源驗證、漏洞掃描與人工抽查。
- [ ] 僅依賴語義檢索或 re-ranking 不能保證安全，因為任務對齊的漏洞條目可同時具備高相關性與惡意資料流；部署時應加入 taint analysis、SAST、依賴檢查與生成後安全驗證。
- [ ] 安全知識注入如 CodeGuarder 能降低但不能消除攻擊成功率，表示防禦不應只在 prompt 中宣告安全規則，還需要對檢索內容做隔離、可信度標註、衝突檢測與最小權限式上下文組裝。

## 限制與未來工作

研究僅評估 85 個人工或 LLM 輔助構造的 function-level snippets、兩種語言、三個生成器與特定 retriever/reranker 設定；未提供更廣泛商用模型、不同檢索架構、真實公共來源滲透率或完整 TWR、CodeBLEU 數據。輸出漏洞判定主要依賴 GLM-5.1 LLM judge，可能存在評估偏差；論文也未展示完整防禦比較與實際部署成本。
